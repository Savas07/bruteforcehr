# ADR 0002 — Data model (Firestore)

- **Status:** Accepted
- **Date:** 2026-10-22
- **Deciders:** Savas (owner), lead engineer agent
- **Supersedes:** BRIEF.md §6.2 (Postgres tables, `user_id` + RLS) and the storage parts of §6.3
- **Related:** [0001-stack.md](0001-stack.md), design research `docs/design/research/job-detail.md`, `docs/design/research/tracker.md`
- **Source of truth in code:** `packages/core` (zod schemas, enums, write-policy constants, status state machine), `packages/api` (paths, converters)

## Context

The brief models data as Postgres tables with `user_id` columns, RLS, JSONB CV revisions, pgvector and Realtime (§6.2, §6.3). ADR 0001 replaced Supabase with Firebase: Firestore `(default)` in `europe-west1`, Security Rules deny-by-default, snapshot listeners instead of Realtime, Firestore offline persistence instead of a hand-written outbox, and Firestore vector search instead of pgvector.

That changes how we express ownership (document paths instead of `user_id` columns), immutability (rules instead of table grants), and indexing (explicit composite indexes). It also needs a schema-evolution story, because older desktop builds and TestFlight builds keep reading the same documents.

Constraints we relied on (checked 2026-10-22):

- Firestore vector search: embedding dimension **≤ 2048**, only a **flat** index type, at most **1000** results per nearest-neighbour query (Standard edition), **no snapshot listeners** on vector queries, and only the server libraries (Python, Node.js, Go, Java) support it. Pre-filtering needs a composite index that combines the filter fields with the vector field. `DOT_PRODUCT` on unit-normalised vectors is recommended over `COSINE` ([Search with vector embeddings](https://firebase.google.com/docs/firestore/vector-search)).
- TTL policies delete **whole documents**, typically **within 24 hours** after expiry. One TTL field per collection group. Absent or `null` TTL fields disable expiry per document ([Manage data retention with TTL policies](https://firebase.google.com/docs/firestore/ttl)). TTL can't clear a single field, so mail-body purging is a scheduled function, not TTL.

## Decision

### Conventions

| Rule                    | Detail                                                                                                                                                                                                                                                                                |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ownership by path       | All user data lives under `users/{uid}`. Rules grant access when `request.auth.uid == uid`. No document stores `userId`.                                                                                                                                                              |
| Document id = entity id | Domain objects have `id`. The converters strip `id` (and `cvId` for revisions) on write and inject them from the path on read. `jobMatches/{jobId}` reuses the job id. `users/{uid}` uses the uid. `appConfig/{platform}` uses the platform. Everything else uses Firestore auto ids. |
| Field names             | camelCase. Enum values are snake_case strings.                                                                                                                                                                                                                                        |
| Time                    | Domain timestamps are `Date`. The SDK `Timestamp` conversion goes through an injected `TimestampAdapter` (`@bfhr/api`), so the JS SDK (desktop), `@react-native-firebase` (iOS) and `firebase-admin` (functions) share one converter.                                                 |
| Absent vs empty         | "Maybe" scalars are stored as `null`, never left out, so `== null` queries work and the SDK never sees `undefined`. Lists default to `[]`. The JSON Resume content is the exception: it follows the JSON Resume spec, where every field is optional.                                  |
| Validation              | Every read and write goes through the zod schema of `@bfhr/core`. Unknown fields are stripped on read. That is how a client tolerates fields from a newer schema (see Migrations).                                                                                                    |
| `schemaVersion`         | Every stored document has an integer `schemaVersion`. `CURRENT_SCHEMA_VERSION = 1`. Converters stamp it on create only. Updates never touch it.                                                                                                                                       |

### Immutability and append-only rules

- **CV revisions** are create-only. "Restore" creates a new revision with `basedOnRevisionId` pointing at the restored one.
- **CV optimistic concurrency.** `version` starts at `CV_INITIAL_VERSION = 1`. Every update sets `version = previous + CV_VERSION_INCREMENT` (1) inside a transaction (`converters.cvUpdate`). The rules reject anything else. A rejected write surfaces the "keep mine / keep theirs / compare" UI (§6.3).
- **Rendered files** are create-only. Their `sha256` identifies the exact bytes an application used.
- **Application pins** (`cvRevisionId`, `cvFileId`, `coverLetterId`, `coverLetterFileId`) are write-once after `appliedAt` is set (§4.4.4). The rules allow `null → value` only.
- **`appliedAt` is never cleared.** Once set it may be corrected to another date, but never back to `null`, even when the application moves back to saved/preparing or an Undo reverses the move into applied. This closes the "reopen to unpin" bypass. The state machine only ever sets `appliedAt` (when it is `null`); `revert` and backward moves leave it untouched.
- **Application events** are append-only. Undo never edits or deletes an event. It appends a user `status_changed` event whose **`revertsEventId`** points at the undone event. The brief's `reverted_by` is derived (`revertedBy(eventId, events)` in `@bfhr/core`), so the collection stays create-only. When an application is deleted, a server trigger deletes its events (clients can't delete events).
- **Mail messages** are server-owned apart from the four review fields above.
- Timeline events never contain mail body text, only the subject line (`text`) and the reason. That way an append-only document never holds data that the retention purge must remove.

### Tracker state machine (`packages/core/src/status.ts`)

- Progress order: saved < preparing < applied < acknowledged < screening < interviewing < offer < accepted | declined. **Accepted/declined are reachable only from offer.** Side exits rejected, withdrawn and ghosted are reachable from any active status (saved … offer), including saved → rejected.
- **Phases** (`statusPhase()`): _Shortlist_ (saved, preparing), _In progress_ (applied → offer), _Closed_ (accepted, declined, rejected, withdrawn, ghosted). Board, iPhone sections, filters and Insights use the same grouping.
- **Automation** (`rule`/`ai`) may only move an active application forward, or to rejected. It never sets accepted, declined, withdrawn or ghosted, and never moves a terminal application. Automated events need `confidence` and `evidence.reason`. Mail-driven ones also carry `evidence.mailMessageId`.
- **The user** may move forward, backward, to any side exit, and reopen or correct a terminal application.
- **Undo** (`canRevert` / `revert`) is offered only while the event is the application's **latest status move**, the application still has the status that event set, and nothing has undone it yet. There's no time limit. Otherwise the UI shows "Can't undo — the status changed since." The undo is a user event, so it may restore moves that the forward rules would otherwise block (e.g. back into accepted after a mistaken reopen). Undoing an automatic change also sets the linked mail's `reviewState` to `corrected` in the same batch.
- **Suggestions** are never applied automatically. `suggestGhosted` fires after `settings.ghostedAfterDays` (21) days without an employer signal (created, status change, mail received, interview scheduled; undone events and undo events are ignored) for applied/acknowledged/screening/interviewing. `followUpDue` fires `settings.followUpAfterDays` (7) days after applying or after the last follow-up sent, while the application is still _applied_ and nothing has come in since.

### Job matches and sources (from the job-detail research)

- `reasons[]` and `gaps[]` hold `MatchFactor` items: `kind` (requirement / skill / experience / other), `facet` (location / remote / authorization / salary / seniority / language — requirements only), `label`, `status`, `impact` (most / some — "Matters most / Matters some", no numeric weights), `evidence` {from: posting / cv / profile, quote} and `source` (rule / ai, so AI items carry the "AI · can be wrong" label).
  - `reasons` take statuses `met`, `partial` and `not_stated`. "Not stated" is neutral, never a gap. The requirements checklist renders `reasons`/`gaps` with `kind == "requirement"`.
  - `gaps` take `missing` (not in the CV yet; correctable with "I have this") and `outside_prefs` (the posting conflicts with preferences).
- Score bands come from `matchBand(score)` with `MATCH_BAND_THRESHOLDS = { strong: 80, good: 65, partial: 45 }`; anything lower is "stretch". The thresholds are provisional and get recalibrated against real score distributions in M4.
- Every match records the CV **and revision** it was computed against, plus `computedAt` ("Based on CV '…' · updated 2 h ago"). Changing the CV re-scores into the same document.
- `dismissReasons[]` is optional and multi-select; it feeds ranking. Hiding a whole company writes to `profile.hiddenCompanies`, not to each match.
- `jobs.sources[]` keeps each listing's own salary, wording, dates and apply route, so "Found on" can group _Direct from employer_ (`isDirectFromEmployer`) above _Job boards_ and show fields that differ. The canonical `applyUrl`/`applyEmail` prefers the direct employer route. The full preference order is confirmed with the Apply research.

### Vector search on `jobs.embedding`

- `embedding` is a Firestore vector field on `users/{uid}/jobs/{jobId}`. Cloud Functions write it (`FieldValue.vector`). It is **not** part of the client model: client rules reject any write containing `embedding` (`JOB_EMBEDDING_FIELD`), and converters strip it on read.
- Nearest-neighbour queries run only in Functions (the client SDKs don't support them). They are scoped to one user's `jobs` collection, use `DOT_PRODUCT` on unit-normalised vectors, and request ≤ 200 neighbours (below the 1000 cap) before the matching pipeline's hard filters and LLM rationale.
- Index: one flat vector index on collection group `jobs`, query scope `COLLECTION`, field `embedding`. A composite variant with `remoteType ASC` + `embedding` covers pre-filtered queries. **The dimension is fixed in M4** together with the embedding model (Anthropic has no embeddings endpoint, so it's a separate provider decision). It must be ≤ 2048. A model change means a new field (`embedding_v2`) plus a backfill, following the expand → contract steps below.

Field overrides:

- **Collection-group** single-field index on `mailMessages.bodyPurgeAt` (ASC) for the purge job (`where bodyPurgeAt <= now`).
- **Index exemptions** for large text that is never queried: `jobs.description`, `mailMessages.bodyText`, `cvs/revisions.content`, `coverLetters.body`. This keeps write cost and index storage down.

### Retention (§8)

- **Non-job mail is never stored.** The pre-filter and classifier run in memory. For `not_job` messages, only a hash of the provider message id is kept under `serverOnly` (for dedupe), with a TTL field that expires after the sync lookback window. `not_job` exists in `MailCategory` only so that a user correction can be expressed. When a stored message is corrected to `not_job`, a trigger deletes the document.
- **Job-mail bodies** (`bodyText`) are kept while the linked application is active. When it becomes terminal, the server sets `bodyPurgeAt = closedAt + settings.mailBodyRetentionDays` (default 180). Reopening sets it back to `null`. Messages not linked to an application (job alerts, unanswered outreach) get `bodyPurgeAt = receivedAt + retention`. A daily scheduled function clears `bodyText` and `snippet` on due documents and keeps the metadata, category and links that Insights need.
- **Disconnect + purge** deletes the account's `mailMessages`, its `serverOnly` secrets, and revokes tokens. **Delete account** recursively deletes `users/{uid}`, `users/{uid}/**` in Storage and the `serverOnly` entries for the uid. **Export** reads the same collections through the converters.

### Schema evolution: `schemaVersion` + expand → contract

1. **Expand.** New fields are added with a zod `.default(...)` (or `.nullable().default(null)`) so documents without them still parse. Readers strip fields they don't know, so older clients ignore new ones. Clients write existing documents only through field-level `update()` (`toFirestoreUpdate`, `mailReviewUpdate`, `cvUpdate`). Full-document `set()` (`toFirestore`) is for creates only, so an old client can never drop a newer field it doesn't know about.
2. **Migrate.** A server migration rewrites documents into the new shape and bumps `schemaVersion`. Readers accept any `schemaVersion ≥ 1`.
3. **Contract.** Once `appConfig/{platform}.minSupportedVersion` excludes every build that doesn't write the new shape, old fields are removed and defaults become required.

Closed enums (`ApplicationStatus`, `MailCategory`, `ReviewState`, …) are part of the contract: an old client fails to parse an unknown value. A new enum value is therefore written only after `minSupportedVersion` has been raised for every platform. Open vocabularies use strings instead of enums: job source ids (`KNOWN_JOB_SOURCES` only labels them), template and font-pair ids.

## Consequences

- Rules are path-based and simple, but some rules are cross-field (CV version step, write-once pins, the four mail fields, user-only client events). They live in `firebase/firestore.rules` and mirror the constants exported from `@bfhr/core` (`CURRENT_SCHEMA_VERSION`, `CV_INITIAL_VERSION`, `CV_VERSION_INCREMENT`, `MAIL_MESSAGE_CLIENT_UPDATABLE_FIELDS`, `MAIL_REVIEW_CLIENT_STATES`, `JOB_MATCH_CLIENT_UPDATABLE_FIELDS`, `CLIENT_EVENT_ACTORS`, `JOB_EMBEDDING_FIELD`). Changing a constant means changing the rules and their CI tests too.
- Insights read `applicationEvents` client-side for one user. That is fine at personal scale; a server aggregate can be added later without a schema change.
- The undo link points backwards (`revertsEventId`). Finding whether an event was undone needs the application's events, which the detail page loads anyway.
- Denormalised copies (cv `templateId`/`theme`, application `company`/`role`/`source`, job `sourceKeys`) must be maintained by whoever writes the source of truth. The schemas validate `sourceKeys` against `sources`.
- Vector search can't back a live listener. The Jobs feed listens to `jobMatches` (computed server-side), not to vector queries.

## Alternatives considered

- **Top-level collections with a `userId` field.** Rejected: every query and rule would need the extra filter, and collection-group queries would be the norm instead of the exception.
- **Mutable `revertedBy` on the original event.** Rejected: it would need an update path on an otherwise create-only collection, and a rule exception that is easy to get wrong. `revertsEventId` on the new event carries the same information.
- **Firestore TTL for mail bodies.** Rejected: TTL deletes whole documents, but Insights need the metadata of old messages. TTL is still used for whole-document expiry in `serverOnly` (OTP challenges, processed-message hashes).
- **Integer `schemaVersion` gating reads (reject newer docs).** Rejected: it would break every old client at the first expand step. Version-tolerant reads plus `minSupportedVersion` gate breaking changes instead.
