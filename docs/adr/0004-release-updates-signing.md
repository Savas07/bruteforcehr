- **Status:** Accepted (revised 2026-10-22 for the client stack switch in [ADR 0007](0007-native-ios-tauri-desktop.md): Tauri 2 desktop, native SwiftUI iOS; the earlier electron-builder/electron-updater and `expo prebuild` + fastlane jobs are removed; revised 2026-10-23 for the M1 implementation: public source repo hosts the releases, keyless Firebase deploys, optional Apple credentials — see the amendments at the end)
- **Date:** 2026-10-22 (revised 2026-10-23)
- **Supersedes:** BRIEF.md §7 (adapted to Firebase, Tauri and native iOS) and the Windows-signing part of BRIEF §3
- **Related:** [0001-stack.md](0001-stack.md), [0006-hosting-domains.md](0006-hosting-domains.md), [0007-native-ios-tauri-desktop.md](0007-native-ios-tauri-desktop.md), [runbooks/release.md](../runbooks/release.md) (secrets inventory), [runbooks/accounts.md](../runbooks/accounts.md)

## Context

- BRIEF §2.2: **GitHub Releases are the single source of truth for versions.** Publishing one release must update the desktop apps, ship iOS to TestFlight, deploy backend changes and refresh the website download page.
- _(Superseded 2026-10-24: the source repo is private and releases live in `Savas07/bruteforcehr-releases`; see the last addendum.)_ The source repo `Savas07/bruteforcehr` is **public** (amendment below). Updating from a private repo would need a GitHub token inside the app (forbidden, BRIEF §2.7); a public repo needs none, so BRIEF §0 ("Public releases repo: source repo if it's public") applies: binaries and the update manifest are published as **GitHub Releases of `Savas07/bruteforcehr` itself**. The release jobs need only the workflow's `GITHUB_TOKEN`. `Savas07/bruteforcehr-releases` stays unused.
- The backend is Firebase (ADR 0001): Firestore rules and indexes, Storage rules, Cloud Functions gen2 (`europe-west1`) and Hosting (`bruteforcehr.web.app`).
- **iOS can't self-update** outside TestFlight/App Store: App Review Guideline 2.5.2 forbids downloading executable code ([App Review Guidelines §2.5.2](https://developer.apple.com/app-store/review/guidelines/#software-requirements)). TestFlight builds are **active for 90 days** ([TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/); [Tech Talk "Get started with TestFlight"](https://developer.apple.com/videos/play/tech-talks/110343/)), and internal testers get builds without Beta App Review ([TestFlight](https://developer.apple.com/testflight/)).
- **iOS CI signing:** `xcodebuild` authenticates with an App Store Connect API key through `-authenticationKeyPath`, `-authenticationKeyID` and `-authenticationKeyIssuerID`, together with `-allowProvisioningUpdates` (`man xcodebuild`, Xcode 26.6). Automatic signing can use **cloud signing**, where certificates are "created and managed on Apple servers" and "accessible only to members of your development team with the Admin role" ([Xcode 13 release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-13-release-notes); [Cloud-managed certificates](https://developer.apple.com/help/account/certificates/cloud-managed-certificates)). `-exportArchive` options (from `xcodebuild -help`): `method` `app-store-connect`, `destination` `upload`, `manageAppVersionAndBuildNumber` (default YES), `testFlightInternalTestingOnly`.
- **macOS:** software distributed outside the Mac App Store must be signed with Developer ID and notarized ([Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)). Tauri signs from `APPLE_CERTIFICATE` (base64 `.p12`) + `APPLE_CERTIFICATE_PASSWORD` (+ `APPLE_SIGNING_IDENTITY`), and notarizes through the App Store Connect API using `APPLE_API_ISSUER`, `APPLE_API_KEY` (**the Key ID**) and `APPLE_API_KEY_PATH` (path to the `.p8`) ([Tauri macOS code signing](https://v2.tauri.app/distribute/sign/macos/)). `--target universal-apple-darwin` builds one universal app ([Tauri CLI](https://v2.tauri.app/reference/cli/)).
- **Windows signing isn't available to this owner now.** Azure Artifact Signing Public Trust is limited to organizations in listed countries and **individuals in the US or Canada** ([Artifact Signing quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart); [FAQ](https://learn.microsoft.com/azure/artifact-signing/faq)). The owner is an individual in Turkey, and an OV certificate on a cloud HSM is postponed until the app is shared (kickoff).
- **Tauri updater:** every update must carry a signature made with our private key, and verification "cannot be disabled". With `bundle.createUpdaterArtifacts: true` and `TAURI_SIGNING_PRIVATE_KEY` (+ `_PASSWORD`) set, `tauri build` writes `myapp.app.tar.gz` + `.sig` on macOS and `myapp-setup.exe` + `.sig` for NSIS on Windows. A **static `latest.json`** needs `version` and `platforms.<os>-<arch>.{url,signature}`, where `signature` is the `.sig` _content_, and "Tauri will validate the whole file before checking the version field". Endpoints can be set at runtime from Rust "such as separate release channels" ([Tauri updater](https://v2.tauri.app/plugin/updater/)). The signatures are minisign/Ed25519 ([ADR 0007](0007-native-ios-tauri-desktop.md)).
- **GitHub "latest":** `/releases/latest/download/<asset>` resolves to the latest release ([Linking to releases](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases)), which is "the most recent non-prerelease, non-draft release". `make_latest` sets it explicitly, and "drafts and prereleases cannot be set as latest" ([Releases REST API](https://docs.github.com/en/rest/releases/releases)).
- GitHub-hosted runners: `macos-26` (Apple silicon, Xcode 26.x), `windows-latest`, `ubuntu-latest` ([runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners); [macos-26-arm64 image](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md)). `github.run_number` "does not change if you re-run the workflow run" ([contexts](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts)).

## Decision

### 1. Versioning

- **Changesets** on `main` (`.changeset/config.json`): every `@bfhr/*` package is in one **`fixed`** group, so all apps share one version `X.Y.Z`; private packages are versioned but never tagged per package (`privatePackages: { version: true, tag: false }`). The desktop app's `tauri.conf.json` sets `"version": "../package.json"`. The schema allows "a path to a `package.json` file containing the `version` field", and Tauri recommends managing the version in its config ([config reference](https://v2.tauri.app/reference/config/#version)). So the Changesets bump of `@bfhr/desktop` is the app version. iOS receives `X.Y.Z` as `MARKETING_VERSION` at build time.
- `version.yml` (on push to `main`) runs [`changesets/action`](https://github.com/changesets/action) v2: while changesets are pending it keeps the **"chore: version packages"** PR up to date. When that PR is merged (no changesets left, no tag for the version yet) it pushes tag `vX.Y.Z`, creates a **draft** release `vX.Y.Z` in `Savas07/bruteforcehr` with the notes, and dispatches `release.yml` on the tag (a tag pushed with `GITHUB_TOKEN` doesn't trigger workflows — [Triggering a workflow from a workflow](https://docs.github.com/en/actions/using-workflows/triggering-a-workflow#triggering-a-workflow-from-a-workflow)). Drafts are never "latest", so updater clients can't see them. The notes are the changeset summaries of that version, merged across the packages' CHANGELOG.md files without dependency-bump lines (`scripts/release`, `notes`).
- Pre-releases (`vX.Y.Z-beta.N`, Changesets pre mode) feed the **beta** channel; the owner pushes the beta tag, which triggers `release.yml` directly.

**Dry run.** `gh workflow run release.yml --ref <ref> -f dry_run=true -f version=X.Y.Z`, or a push to a branch `release-dry-run/X.Y.Z` (needed to test pipeline changes before they reach `main`: `workflow_dispatch` only sees workflows that exist on the default branch). If any job fails, the draft stays unpublished and no `latest.json` is served. The backend job may already have deployed, which is safe because backend changes are expand-only. A re-run of the `ios` job keeps `GITHUB_RUN_NUMBER`, so if the upload already succeeded, retry with a new patch tag instead of re-running.

### 3. Client update behaviour

**Desktop (`tauri-plugin-updater`, static `latest.json` in the GitHub Releases of `Savas07/bruteforcehr`)**

- Endpoints (committed in `apps/desktop/src-tauri/tauri.conf.json` → `plugins.updater`):
  - **Stable:** `https://github.com/Savas07/bruteforcehr/releases/latest/download/latest.json` (`endpoints`).
  - **Beta:** `https://github.com/Savas07/bruteforcehr/releases/download/updater-beta/latest.json` (`betaEndpoints`, read by the app's Rust code; the plugin ignores unknown keys).
  - The Settings channel (**Stable / Beta**) picks the endpoint at runtime in Rust (`updater_builder().endpoints(…)`).
- Checks at launch and every 6 h, and downloads in the background (`download`). Shows a non-blocking "Restart to update" with the release notes. `install` + `relaunch` run only on that action or at quit, and never interrupt unsaved edits. On Windows, "Tauri will automatically quit your application before installing updates", so pending writes are flushed in `on_before_exit`. `windows.installMode` is `passive` ([Tauri updater](https://v2.tauri.app/plugin/updater/)).
- **Integrity on every OS:** the updater refuses any bundle whose Ed25519 signature doesn't match the embedded public key (key id `C39774B86CA8CBE9`, generated 2026-10-23). `requireSignedVersion: true` also rejects a manifest that pairs a version with an artifact signed for another version (a downgrade through a crafted `latest.json`): the Tauri CLI writes `version:X.Y.Z` into the signature's trusted comment, and `publish` refuses signatures without the release's version. **macOS** bundles are also Developer ID-signed and notarized once the Apple secrets exist; until then they are ad-hoc signed (§2).
- **Windows (unsigned until a certificate exists):**
  - The first install shows the **SmartScreen "Windows protected your PC"** warning ("More info → Run anyway") ([SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation); Tauri notes signing prevents it — [Windows code signing](https://v2.tauri.app/distribute/sign/windows/)).
  - Updates **are** verified: someone with write access to the repo's releases but without the updater private key can't push code to installed clients. The trust anchor becomes the updater private key (CI secret + offline backup, [runbooks/release.md](../runbooks/release.md)).
  - When a certificate is added: configure `bundle.windows.certificateThumbprint` or `signCommand` (Azure Key Vault/Artifact Signing via `signCommand` — [Windows code signing](https://v2.tauri.app/distribute/sign/windows/)). Updater signatures are independent and keep working.
- **No staged rollout percentage:** the static `latest.json` has no equivalent of `stagingPercentage`. A rollout reaches all clients of the channel at their next check. A dynamic update server (a Cloud Function answering 200/204 per client — [Tauri updater](https://v2.tauri.app/plugin/updater/)) is the path if staging is ever needed.
- **iOS:** TestFlight automatic updates, plus an in-app check against `appConfig/ios`: a banner "Update available in TestFlight" when `latestVersion` > installed, and a blocking screen when installed < `minSupportedVersion`.

### 4. Channels

| Channel | Source                                                                                                        | Desktop                                         | iOS                                         |
| ------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------- |
| Stable  | published, non-pre-release GitHub Release marked latest                                                       | default; `releases/latest/download/latest.json` | TestFlight internal group                   |
| Beta    | GitHub pre-release `vX.Y.Z-beta.N`; manifest in pre-release `updater-beta` (also updated for stable versions) | opt-in in Settings                              | same TestFlight group (iOS has one channel) |

The 90-day TestFlight expiry means **at least one release every ~80 days**. `publish` records `updatedAt` in `appConfig/ios` whenever a build reached TestFlight, and a scheduled CI workflow opens an issue when the latest iOS build is older than 75 days. App Store distribution (also release-triggered) is the later alternative if the app is shared publicly.

### 5. Rollback

- **Never delete** a published release that clients may have installed. Ship `X.Y.Z+1` with the revert.
- **Halt a bad desktop release:** replace the `latest.json` asset of the bad release (and of `updater-beta`) with the previous release's `latest.json` (`gh release upload … --clobber`). The default comparator only updates when "`update.version > current`", so clients that haven't updated stay put. Clients that already updated keep the bad version until `X.Y.Z+1`.
- iOS: expire the bad build in App Store Connect → TestFlight. Testers keep the previous build installable.
- Backend: Functions roll back by redeploying the previous tag's `backend` job (re-run on the old tag with `--only functions`), and rules the same way. Data changes are expand-only, so no data rollback is needed.
- Website: `firebase hosting:rollback` or redeploy the previous tag.
- Raise `minSupportedVersion` only after the fix is out, never as a rollback tool.

### 6. Secrets

All release credentials are **CI-only** GitHub Actions secrets on `Savas07/bruteforcehr`: the Tauri updater key + password, the Workload Identity Federation provider + deploy service account (identifiers, no key), and — once the owner has them — the Apple API key and the Developer ID certificate. No cross-repo token is needed: releases live in the same repo and use the workflow's `GITHUB_TOKEN`. Names, scopes, consumers and rotation are listed in **[runbooks/release.md](../runbooks/release.md)**. Runtime secrets (`ANTHROPIC_API_KEY`, OAuth client secrets, token-encryption key, job API keys) live in **Secret Manager** ([runbooks/accounts.md](../runbooks/accounts.md)). None of them ever ship in a client bundle. Only the updater **public** key is embedded in the desktop app.

**Firebase/GCP from CI is keyless.** Workload Identity Federation pool `github`, OIDC provider `bruteforcehr-repo` (issuer `https://token.actions.githubusercontent.com`, attribute condition `assertion.repository == 'Savas07/bruteforcehr' && assertion.repository_id == '1429601845'`; to be narrowed to `release.yml` on `v*` tags in the `release` environment, command in [runbooks/release.md](../runbooks/release.md) "Release environment and deploy identity"), and service account `github-deployer@bruteforcehr.iam.gserviceaccount.com`, which only principals with `attribute.repository/Savas07/bruteforcehr` may impersonate (`roles/iam.workloadIdentityUser`). ## Consequences

- One tag drives every platform. A failed platform blocks publication, so versions stay aligned.
- Windows users see a SmartScreen warning on first install. Accepted for personal use, and **must be revisited before sharing the app**. Unlike the earlier electron-updater design, Windows updates are cryptographically verified.
- The Tauri updater private key is a single point of failure: if it leaks, an attacker who can also publish to the releases repo can ship updates; if it's lost, installed clients can't update (rotation needs a release signed with the old key that embeds the new public key — runtime `pubkey` exists for that, [Tauri updater](https://v2.tauri.app/plugin/updater/)).
- No staged rollouts (see §3). Halting is manual, per §5.
- iOS needs a release at least every 90 days or the app stops launching from TestFlight.
- Public repo: GitHub-hosted macOS and Windows runners are free, so every release builds all platforms in CI.
- A Ruby/fastlane toolchain is no longer needed for iOS. `xcodebuild` handles API-key auth, cloud signing and upload natively.

## Amendment — 2026-10-22: Linux-only automatic CI

GitHub Actions stopped starting jobs on the private repo (free minutes / spending limit). The owner chose to **keep the repo private and run automatic CI on Linux only** (`ci.yml`: lint, typecheck, tests, BFHRCore `swift test` in the Swift container, security-rules emulator tests, gitleaks, audit). `desktop.yml` (macOS + Windows build, E2E, real-app captures) is **manual-only** (`workflow_dispatch`).

Consequences for M1, to be decided at M1 kickoff: the `desktop-mac`, `desktop-win` and `ios` release jobs above need macOS/Windows runner minutes. Options: (a) owner funds minutes for release runs only; (b) build, sign and notarize the macOS app and the iOS archive locally on the owner's Mac with a scripted, reproducible release command, and build Windows only via a manually triggered run; (c) make the repo public (free runners). Until then the release flow above is the target design, not an automatic one.

**Resolved the same day: option (c).** The owner made `Savas07/bruteforcehr` public after a history audit: gitleaks over the full history (one false positive: a keyboard key name), no secrets or personal data in tracked files (commits use the GitHub noreply address; the Firebase iOS API key is client config, limited to Firebase services and now to bundle id `com.savas07.bruteforcehr`; the Apple Team ID is not secret). Standard GitHub-hosted runners are free for public repos, so `desktop.yml` runs automatically again on desktop changes, and the release jobs above can run as designed. Secrets stay in GitHub Actions secrets and Secret Manager; pull requests from forks don't receive them.

## Alternatives considered

## Amendment — 2026-10-23: M1 implementation

- Releases, `latest.json` and `updater-beta` live in **`Savas07/bruteforcehr`** (public), per BRIEF §0. `RELEASES_REPO_TOKEN` is dropped; `Savas07/bruteforcehr-releases` is unused.
- The owner has no Developer ID certificate or App Store Connect API key yet. Their consumers are configuration-gated (§2): unsigned-but-ad-hoc macOS builds, no notarization, an unsigned iOS archive without TestFlight upload, each with a `skipped:` log line naming the missing secret. Adding the secrets turns them on with no workflow change.
- Build jobs hand files to `publish` as workflow artifacts instead of uploading to the draft themselves, so a partial release is never visible and only `publish` needs `contents: write`.
- `publish` verifies the updater signatures against the committed public key before anything is published, and adds `SHA256SUMS.txt` for the website's download page.
- `appConfig` uses the `AppConfigSchema` fields (`updatedAt`, not `publishedAt`), takes `minSupportedVersion` from the committed `scripts/release/min-supported-versions.json` (a changeset can't carry custom flags), and `appConfig/ios` is written only when the version reached TestFlight, so the iOS banner never points at a build that doesn't exist.
- Dry runs (§2) prove the pipeline without publishing; `release-dry-run/X.Y.Z` branches exist because `workflow_dispatch` only works for workflows already on `main`.

## Addendum — 2026-10-24: private source, public releases repo

The owner makes **`Savas07/bruteforcehr` private**. Everything users and installed apps reach stays public in **`Savas07/bruteforcehr-releases`** (public, issues enabled), the BRIEF §0 "public releases repo" case. This supersedes the "public source repo" parts of the Context, §4, §6, the 2026-10-22 resolution and the 2026-10-23 amendment; the pipeline design (§1–§5) is unchanged.

- **What's public:** GitHub Releases `vX.Y.Z` (installers, updater bundles + `.sig`, `latest.json`, `SHA256SUMS.txt`, the Changesets notes, unchanged), the `updater-beta` pre-release with the beta manifest, and **public support issues** (user decision U4; README and issue form there repeat "issues are public, don't include personal data"). The repo holds only a README and the issue template, so each release tag points at its default-branch commit; the source tag `vX.Y.Z` stays in the private repo (`version.yml`).
- **Updater endpoints** (`tauri.conf.json`): `https://github.com/Savas07/bruteforcehr-releases/releases/latest/download/latest.json` (stable) and `…/releases/download/updater-beta/latest.json` (beta). Clients still need no token (BRIEF §2.7). Asset URLs in `latest.json` and `appConfig` (`downloadUrl`, `releaseNotesUrl`) point at the releases repo. The website reads that repo's Releases API at build time without a token (CI passes its `GITHUB_TOKEN` only for the rate limit).
- **Cross-repo token:** `release.yml` drafts, uploads to and publishes the release, and maintains `updater-beta`, with the Actions secret **`RELEASES_REPO_TOKEN`**: a fine-grained PAT owned by `Savas07`, repository access **only `Savas07/bruteforcehr-releases`**, permission **Contents: Read and write** (Metadata: read is implied), **expiry 1 year**. A real release fails in `prepare` when it's missing. **Rotation:** yearly before expiry, or at once if it may have leaked: create a new token, `gh secret set RELEASES_REPO_TOKEN`, revoke the old one (docs/runbooks/release.md). A leaked token can rewrite releases but not forge updates: clients reject any bundle not signed with the Tauri updater key, which never leaves CI secrets.
- **Migration (once):** v0.2.2 was mirrored into the releases repo (installers, bundles, signatures, `SHA256SUMS.txt` without the `latest.json` line; no `latest.json`, because its URLs pointed at the source repo), so the website keeps a download. Installs ≤ 0.2.2 poll the source repo's manifests, so **v0.3.0** is also published there by a clearly marked `BRIDGE v0.3.0` step in `release.yml` (its `latest.json` only, whose URLs already point at the releases repo), skipped automatically once the source repo is private. The owner flips the repo to private only after v0.3.0 is out, then deletes the bridge step. Installs that were offline during that window must download 0.3.0 or later from the website once.
- **Actions minutes:** a private repo on GitHub Free has 2,000 minutes/month, with macOS minutes counted ×10 and Windows ×2. Ubuntu CI stays on every push/PR; macOS/Windows workflows run only on relevant paths, on demand and in releases (budget in docs/runbooks/release.md "Actions minutes"). This replaces the "free runners" consequence above.
- **Pipeline changes:** `version.yml` only pushes the source tag and dispatches `release.yml`; `prepare` drafts the release in the releases repo (no `--verify-tag`: the tag is created there when `publish` publishes the draft). `release.yml` also calls `desktop.yml` as `verify-desktop` (macOS + Windows E2E), which `publish` needs. Rollback commands (§5) take `--repo Savas07/bruteforcehr-releases`.
- Workload Identity Federation is unaffected: its condition matches `repository` + `repository_id`, which don't change with visibility.
