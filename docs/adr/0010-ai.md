# ADR 0010 — Server-side AI: Claude provider, grounding check, CV import and assists

- **Status:** Accepted
- **Date:** 2026-10-23
- **Deciders:** Savas (owner), lead engineer agent
- **Related:** [0001-stack.md](0001-stack.md), [0002-data-model.md](0002-data-model.md), [0008-auth-email-link.md](0008-auth-email-link.md), ADR 0009 (cv-render, branch m2/cv-render), [runbooks/accounts.md](../runbooks/accounts.md) §2, BRIEF §2.4, §4.5, §6.5

## Context

M2 (CV Studio) needs two AI features: **import** an existing CV (PDF, DOCX, JSON Resume, LinkedIn export) into JSON Resume, and **assists** that rewrite, shorten, strengthen or translate CV text (EN/TR/DE). BRIEF §2.4 says AI never invents content. The user's Anthropic key lives in Secret Manager (`ANTHROPIC_API_KEY`); clients never call the model.

## Decision

### Package and callables

- `packages/ai` (`@bfhr/ai`, TypeScript source, inlined into the functions bundle) holds the provider, prompts, extractors, grounding checker and orchestration. It has no Firebase dependency. Spend is recorded through a `UsageLedger` interface, and the Firestore implementation lives in `apps/functions`.
- Callables `cvImport` and `cvAssist` in the `default` codebase, region europe-west1. Their request/response contracts are zod schemas in `@bfhr/core` (`src/ai.ts`), shared with clients:
  - `cvImport({ storagePath, kind: 'pdf'|'docx'|'json'|'linkedin-zip' })` → `{ resume, confidence, warnings, model, promptVersion }`. The file is uploaded first to `users/{uid}/cv-imports/{fileId}`, and the path's uid must be the caller's. `resume` is JSON Resume without `meta`. `confidence` maps a JSON pointer to a value 0..1 for every leaf. `warnings` are codes (`CV_IMPORT_WARNING_CODES`) of the form `code` or `code:detail`.
  - `cvAssist({ text, action, targetLanguage?, context: { section, role?, company? } })` → `{ suggestions: [{ text, placeholders }], model, promptVersion }`, with 0–3 suggestions.
  - Errors are `HttpsError`s with `details.reason` from `AI_ERROR_REASONS` (`email_unverified`, `ai_disabled`, `daily_cap`, `file_not_found`, `unreadable_file`, `no_text`, `file_too_large`, `ai_unavailable`, `ai_invalid_output`).
- Every request needs `auth` and `email_verified` (same rule as `firestore.rules`).

### Models (verified 2026-10-23 in the [models overview](https://platform.claude.com/docs/en/about-claude/models/overview), [pricing](https://platform.claude.com/docs/en/about-claude/pricing) and `GET /v1/models`)

| Task              | Model                                   | Effort | Thinking                                                              | Why                                                                                                                       |
| ----------------- | --------------------------------------- | ------ | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Import (PDF/DOCX) | `claude-sonnet-5-5` ($2 / $10 per MTok) | `low`  | `between_tools` (no up-front thinking; Sonnet 5.5 rejects `disabled`) | Eval: 99.3% of fields correct and 1 extra value, against 98.3% and 17 extras for `claude-haiku-5-5`. About $0.019 per CV. |
| Assists           | `claude-sonnet-5-5`                     | `low`  | `between_tools`                                                       | Better writing in TR/DE. About $0.003 per request.                                                                        |

Dateless ids are pinned snapshots, so a prompt version keeps its behaviour. Haiku 5.5 ($0.10 / $0.50) remains the cheaper option: `eval/report-claude-haiku-5-5-default.md` shows the trade-off.

### Provider

- `AnthropicProvider` sends Messages API **JSON outputs** (`output_config.format`, a schema compiled from zod by `zodOutputFormat`) and validates every reply against the original zod schema again. Validation failures and non-JSON replies are retried.
- **Retries:** at most 3 attempts. Exponential backoff (1 s, 2 s, cap 10 s) with full jitter, honouring `retry-after` up to 20 s. Retried: 408/409/429/5xx/529 and connection errors. Not retried: auth (401/403), bad requests and refusals. A reply that hits `max_tokens` fails at once. The SDK's own retries are off, so every billed attempt is counted.
- The system prompt is sent with `cache_control: ephemeral`.
- The import output schema is generic: items of `{ section, fields[{key,value}], lists[{key,values}], confidence, uncertain }`, with enum sections and keys. A typed object of all twelve JSON Resume sections fails with "compiled grammar is too large", and so did hybrid variants (measured 2026-10-23). `groundImport` checks again that each key is allowed for its section.

### Prompts

Prompts are versioned constants in `packages/ai/src/prompts/` (`cv-import@1`, `cv-assist@1`). The version is returned to clients and logged. Changing the text or schema means bumping the version and re-running the eval. User content always sits inside tags (`<cv_text>`, `<text>`, `<role>`, `<company>`), and the prompts tell the model to treat it as data, never as instructions.

### Grounding check (BRIEF §2.4)

`packages/ai/src/grounding` is deterministic and language-aware. The source text is folded: case, diacritics, Turkish İ/I/ı, `ß`. Then:

- **Numbers** compare by value across notations: `1,500` = `1.500` = `1.5k`, `€1.2M` = `€1,200,000`, Turkish `%18` = `18%`, German `1,5 Mio.`, `3x`. Number words (`five`, `drei`, `iki`) count too; ambiguous words are excluded.
- **Dates** compare at the precision the output claims. `Mar 2021`, `03/2021`, `03.2021`, `März 2021` and `Mart 2021` all read as `2021-03`. A month or day that the source never states counts as fabricated. A bare year may also match a plain number.
- **Entities** must occur in the source, as a word or phrase, in singular/genitive form, as a ≥5-letter stem (Turkish/German inflection), with a Turkish case suffix stripped (`Siemens'te`), or through a small table of translation equivalents (language, country, city, degree and institution words). Entities are acronyms, CamelCase, alphanumeric and tech tokens (`S3`, `Node.js`, `C++`, `S/4HANA`, CEFR levels), emails and URLs. In English and Turkish output, capitalized mid-sentence words also count. German capitalizes every noun, and translations rename job titles, so translations and German output use the `hard` policy.
- **Compounds** are checked per part (`KPI-Projekten`, `GPT-4`).

How the check is applied:

- **Import:** a value the source does not contain is removed, never repaired, with warning `dropped_ungrounded:<pointer>`. Names and titles must appear verbatim (confidence factor 1) or have every word in the source (0.85). Free text must have no ungrounded number, date or entity and at least 90 % of its words in the source. When the month of a date is not in the source, only the year is kept (`date_month_dropped`). Confidence = model item confidence × 0.6 when the model marked the key uncertain × the grounding factor.
- **Assists:** ungrounded numbers become `[X]`/`[X%]` and ungrounded dates `[date]`. Free-form placeholders (`[e.g. 20%]`) are normalized to those three. A suggestion with an ungrounded entity is dropped. If every suggestion is dropped, the model gets one more call that names the offending terms. Suggestions that only echo the input are removed.

### Imports without a model

- **JSON Resume** is validated directly: unknown fields and `meta` are dropped, and invalid values are removed with `dropped_invalid:<pointer>`.
- **LinkedIn "Download your data" ZIP** is mapped column by column (`linkedin-zip@1`) from Profile, Email Addresses, PhoneNumbers, Positions, Education, Skills, Languages, Certifications, Projects, Honors, Publications and Volunteering CSVs, with RFC 4180 parsing and "Notes:" preambles skipped.
- Both report `model: "none"`, have confidence 1, and need neither the AI toggle nor budget.

PDF text comes from pdf.js (`pdfjs-dist` legacy build) in content-stream order, with line and gap reconstruction. DOCX text comes from mammoth. A PDF with fewer than 40 letters is a scan, rejected with `no_text` (no OCR). Text is capped at 40,000 characters (`source_truncated`).

### AI toggle

`Profile.aiEnabled` is a new required field in `@bfhr/core`, with `DEFAULT_AI_ENABLED = true`. The `@bfhr/api` profile converter reads documents written without it as `true`, and so does the server (`aiEnabled === false` refuses). It gates PDF/DOCX import and all assists. Sending email text to AI stays the separate M5 toggle, `settings.aiMailTextAllowed`. Swift `Models.swift` and the conformance JSON are regenerated.

### Per-user daily cost cap

- The cap is **$0.50 per user per UTC day** (`DAILY_COST_CAP_MICRO_USD`). For one user that is at most ~$15 a month, under the ₺250 budget alert, while still allowing about 25 imports or 150 assists a day.
- A **project-wide ceiling** of $3.00 per UTC day across all users (`PROJECT_DAILY_LIMITS.aiMicroUsd`, `serverOnly/projectUsage`) is reserved in the same transaction as the per-user cap (M6 security review finding 4); when it is reached, `DailyCapError("project")` maps to `resource-exhausted` / `daily_cap` with "AI help has reached today's limit for everyone". Sign-up is invite-only. See [runbooks/limits.md](../runbooks/limits.md).
- The ledger is `serverOnly/aiUsage/users/{uid}/aiUsageDays/{YYYY-MM-DD}` with `{ microUsd, requests, day, expireAt, updatedAt }`, and rules deny clients.
- Before each model call, a transaction reserves the worst case: one token per 2.5 characters + 2,000, plus `max_tokens` output, at list price. If the reservation would pass the cap, the request fails with `resource-exhausted`/`daily_cap`. After the call, the reservation is replaced by the actual cost, failed attempts included.
- `expireAt` is 35 days after the day. The TTL policy for collection group `aiUsageDays` is declared in `firebase/firestore.indexes.json` and goes live with the next indexes deploy. Account deletion must also delete `serverOnly/aiUsage/users/{uid}`.

### Logging

One `ai_request` line per call (`AiLogEvent`). It holds enums, model, prompt version, latency, attempts, token counts, cost, source length and grounding counts. It never holds CV text, model replies, file names, emails or the uid. Unexpected errors are logged by error name only.

### Eval

`pnpm --filter @bfhr/ai eval` runs against the live API with `ANTHROPIC_API_KEY`, under a budget (`--budget-usd`, default 3) enforced by the same ledger code.

- **Fixtures:** 16 synthetic CVs (6 EN, 5 TR, 5 DE; 10 PDF, 6 DOCX; single-column, sidebar, Lebenslauf table and compact layouts) rendered by `eval/build-fixtures.ts`, and 15 assist cases.
- **Report** (`eval/report.md`): field accuracy per field and per language, an independent fabrication audit, values removed by grounding, and cost.
- **Result 2026-10-23:** 749/754 fields correct (99.3 %), **0 fabrications**, 0 ungrounded values in any assist suggestion, $0.34 total.

The CI-safe offline suite is `pnpm --filter @bfhr/ai test`. It runs the 34 grounding adversarial cases in `eval/adversarial.ts`; checks that every fixture's true values survive grounding (no false drops); and covers the extractors, the LinkedIn/JSON mappers, provider retries and budget accounting.

## Addendum 2026-10-24 — Applying: tailoring and cover letters (BRIEF §4.4, §9)

### Callables

Both are in the `default` codebase (europe-west1, 120 s timeout), need `auth` + `email_verified`, refuse with `ai_disabled` when `profile.aiEnabled === false`, and run every model call through the same `UsageLedger` as the other features, so they count against the **$0.50 per-user day** and the **$3.00 project-wide ceiling** ([runbooks/limits.md](../runbooks/limits.md)). Contracts are zod schemas in `@bfhr/core` (`apply/`, `coverLetters/`) and Swift models in BFHRCore. New error reasons: `cv_not_found`, `job_not_found`, `template_not_found` (`not-found`). Inputs are read from `users/{uid}/…` only, so another user's ids are simply not found.

- `cvTailor({ cvId, revisionId, jobId, locale, intensity })` → `{ edits, dropped, model, promptVersion }`. An edit is `{ id, path, op: replace|insert|remove|reorder, before, after, order, reason, groundedIn[] }`; `path` is a JSON pointer into the revision's content using **original** indices, `before` always comes from the CV (never the model), `reason` is in `locale` (the UI language) while edits keep the CV's language. `light` rewords bullets, summaries, descriptions and keywords and reorders bullets and keywords; `thorough` also touches the headline, the summary, skill group names, inserts/removes bullets and keywords and reorders skills, projects and sections (`TAILOR_TARGETS`). Names, titles, employers, schools, degrees, dates, locations and contact details are never editable. The client applies the accepted edits with `applyTailorEdits(content, edits, acceptedIds)` (pure; replacements first, then each array's inserts/removals/reorder by original index, deepest first; stale or conflicting edits are skipped) and writes the new revision with `source: "ai_tailor"`, `jobId`, `basedOnRevisionId` ([ADR 0002](0002-data-model.md) "M4 Apply addendum"). The Swift port `Tailoring.apply` is proven by `packages/core/conformance/apply.json`.
- `coverLetterDraft({ cvId, revisionId, jobId, tone: formal|warm|concise, language, templateId? })` → `{ subject, body, placeholders, unresolvedFields, droppedSentences, model, promptVersion }`. `templateId` is a starter template (`starter-en|tr|de`) or one of the user's `coverLetters` documents with `isTemplate: true`; the draft keeps its greeting, closing and fixed sentences. Known merge fields are filled (`role`, `company` from the job; `name`, `email`, `phone` from the profile, else the CV; `job_source`); the rest stay as `{field}` tokens and block sending.

### Grounding

- **Tailoring** (prompt `cv-tailor@1`): each proposal must be an allowed path/operation for the intensity, change something, contain no brackets, and its new text must pass `findUngrounded` against **the entry it edits plus the skills section** (the whole CV for headline, summary and skills) — so a number, technology or result can't move from one job to another. It must also not mention a **job-only term**: the posting's skills and entity-like terms of its description that the CV doesn't contain (this catches lower-case skills like "kafka" that the entity heuristics miss). A failing proposal is dropped, never repaired; the response reports how many.
- **Cover letters** (prompt `cover-letter@1`): the model returns labelled sentences (`candidate` / `company` / `other`). A sentence in the first person (per-language markers; Turkish verb endings) counts as `candidate` whatever its label. Candidate sentences are checked against the CV + template + the job's company and title and must not mention a job-only term; company sentences against the posting; other sentences against everything. Unknown numbers and dates become `[X]`/`[X%]`/`[date]`; a sentence with an unsupported entity or term is removed. When more than half of the letter is removed (or fewer than 3 sentences survive), the model gets one retry naming the offending terms. Greeting and closing fall back to the language's standard lines if they don't pass.

### Models

`claude-sonnet-5-5`, effort `low`, for both. The eval (below) compared Haiku 5.5: also 0 fabrications after the checks, about 13× cheaper, but **49 % of its tailoring proposals were dropped by the checks** (Sonnet: 22 %) and twice as many letter sentences were removed, i.e. it relies on the checker instead of following the rules. At ~$0.011 per request Sonnet allows ~45 tailorings or drafts per user per day under the cap.

### Eval and CI gate

`packages/ai/eval/apply/`: 12 synthetic postings for 12 of the import-eval CVs (4 EN, 4 TR, 4 DE; two English postings for a Turkish and a German CV), each **baiting** with requirements the CV lacks (e.g. Rust, ECMO, Elixir, LucaNet). `pnpm --filter @bfhr/ai eval:apply` runs 12 tailorings (light/thorough alternating) and 12 letters (three tones, one starter template per language) live and records the replies; `eval/apply/gate.test.ts` replays them in CI (`pnpm turbo run test`). The gate fails on **any fabricated item** found by an audit independent of the pipeline's grounding path: every entity/number/date in an edit must be in the CV and every one in a letter in the CV, posting, template or the app's own letter formulas; no bait term in an edit or in a first-person letter sentence; no digit run the sources lack. It also requires ≥ 75 % of tailorings with edits, every edit applying cleanly, ≥ 90 % letters in the requested language and every letter naming the company. Result 2026-10-24 (`eval/apply/report.md`): **0 fabrications**, 54 edits kept / 15 dropped, letters 12/12 in language and naming the company, **$0.26** for all 24 requests ($0.011 tailoring, $0.010 letter). A prompt change invalidates the recording (prompt hash) and fails the gate until the eval is re-run.

## Consequences

- One call per import; no second "verify" model call. The grounding check is cheap and deterministic, but heuristic: it may drop a true value (it then reports a warning, so the user can type it in) and does not judge meaning (a reworded claim with the same words passes). The eval and adversarial cases guard both directions, and new failure cases go into `eval/adversarial.ts`.
- **Scans need OCR,** which is not supported (`no_text`).
- **Adding a JSON Resume section or key** means updating `IMPORT_SECTIONS`, bumping the prompt version and re-running the eval.
- **Deploying `functions:default`** grants the compute service account `secretAccessor` on `ANTHROPIC_API_KEY` (done by the Firebase CLI on 2026-10-23).
