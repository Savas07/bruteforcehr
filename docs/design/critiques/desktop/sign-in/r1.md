## Design Critique: Sign-in with an email link (desktop) — round 1

Context: M1 sign-in for the Tauri desktop app, after the owner's switch (2026-10-23) from a mailed code to Firebase Authentication's passwordless email link. The window is gated: signed out it shows only the sign-in column; the link comes back as `bruteforcehr://auth/finish?link=…` from the website's `/auth/finish` page. Research: `docs/design/research/onboarding-signin.md` (desktop email step, waiting state, errors; written for a code and adapted to a link here) plus two Mobbin rounds below. Persona: Deniz (`deniz.aksoy@example.com`; a Gmail address for the "Open Gmail" states). Stage: first implementation, English.

Captures judged: `pnpm --filter @bfhr/desktop capture:design sign-in --axe`: all 18 sign-in states (`authDesignStates` in `src/design/matrix.ts`) × WebKit (macOS chrome) + Chromium (Windows chrome) × light + dark = 72 PNGs, `artifacts/screens/desktop/harness/{webkit,chromium}/sign-in-*.png` (1280×800), 72 axe reports.

### Overall Impression

Calm and single-purpose. Every state has one clear next step, and nothing in the window suggests the app is there before sign-in. The waiting screen holds up against the references. The weak spots are in the error states, where the secondary action doesn't always fit the cause.

### Visual Hierarchy

- **What draws the eye first**: the email step's app mark, then the title. The waiting state's teal mail icon, then "Check your email". Errors use a neutral grey icon, never red: calm, as the principles ask.
- **Reading flow**: icon → title → one sentence (with the address in bold) → helper → primary → quiet secondary line → back link. The same order in every state.
- **Emphasis**: one primary per state ("Send sign-in link", "Open Gmail", "Sign in", "Send a new link", "Try again"). "Send again" is primary only when there's no inbox button.

### Consistency

| Element | Issue                                                                                                                                                   | Recommendation |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| Column  | 400 px centred on `surface-canvas`, the macOS drag row on top. Same as the "Update required" gate's structure (icon in a 48 px circle, `title1`, body). | —              |
| Buttons | `lg` primary everywhere. The email and confirm forms make it full width (form submit); stand-alone actions size to their label.                         | —              |
| Errors  | Inline `InlineAlert` (`role="alert"`) for send failures, as in the rest of the app. Field errors under the field.                                       | —              |

### Accessibility

- **Color contrast**: axe (WCAG 2.1 A/AA): 0 violations in all 72 states. The disabled "Send again in 0:42" is exempt and has a reason (tooltip + description).
- **Targets**: buttons are 32–40 px tall. Legal links are inline text buttons.
- **Text readability**: body 15 px, helper 13 px, no truncation. The address wraps (`break-all`) rather than overflowing.

### What Works Well

- The address is always visible where it matters (waiting screen, the "send a new link" errors).
- "Open Gmail" opens the inbox of the right Google account (`authuser=`).
- The countdown is shown, not announced. Screen readers hear once when sending again is possible.

### Priority Recommendations

1. **Say where the new link goes** on the invalid/expired screens.
2. **Drop the way back on retryable errors**: the link still works.
3. **Rename the confirm step's back action** to what it does.
