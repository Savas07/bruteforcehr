## Design Critique: Sign-in with an email link (desktop) — round 3

Context: the same 18 sign-in states in the real Tauri shells (WKWebView on macOS, WebView2 on Windows), design build (`pnpm build:e2e:design`), captured by `e2e/capture/capture-design.e2e.ts`. Plus the production E2E build, which runs the real flow against the Firebase Auth emulator with deep links opened through the OS.

Captures judged: CI run [39927355856](https://github.com/Savas07/bruteforcehr/actions/runs/39927355856) (`gh workflow run desktop.yml -f design_capture=true -f screens=none -f auth_states=all`, commit `d9dc095`), artifacts `desktop-design-screens-{macos,windows}-latest`: 18 states × light + dark per OS = 72 PNGs (`macos/design/sign-in-*.png`, `windows/design/sign-in-*.png`). Neither runner's display fits a 1280×800 window at 100 %, so these captures are taken at 75 % zoom (`e2e/capture/helpers.ts`): same layout, lower pixel density.

### Overall Impression

WKWebView and WebView2 render the column the same as WebKit and Chromium in the harness: same wrapping, same icon circles, same focus and error colours. Nothing new to fix in the layout.

### Usability

| Finding                                                                                                                                                                                                                                                                                                                                                                                    | Severity             | Recommendation                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------- | ---------------------------------------------------------------------------------- |
| In the E2E build, pressing Enter in the email field through the embedded WebDriver didn't submit, so the first CI runs looked like "sending fails". The driver sends keys as script events, and a script Enter doesn't trigger implicit form submission. A real key press does, as the harness probe (r2) and a Playwright run of the E2E-mode frontend against the local emulator showed. | 🟢 Minor (test only) | The E2E helpers press the submit button. The product keeps native form submission. |
| Window controls aren't in WebDriver captures, which show the webview only. On macOS the traffic lights are native and the sign-in column keeps a 52 px `data-tauri-drag-region` row. On Windows the native title bar sits outside the webview. So the window can be moved and closed while signed out (by construction, `SignIn.tsx` + `window.rs`).                                       | —                    | Pass.                                                                              |
| The real deep-link path: on the installed macOS app (`/Applications`, LaunchServices) and on Windows (second instance → single-instance hand-off), a crafted link pointing at another domain and a malformed link both land on "This sign-in link doesn't work". The UI can't call the deep-link plugin's commands.                                                                        | —                    | Pass (`e2e/specs/auth.e2e.ts`).                                                    |

### Visual Hierarchy / Consistency

- Dark mode on Windows: the invalid-address state keeps the danger border and outline while focused, and the error line has its icon. The primary stays the strongest element.
- Dark mode on macOS: the neutral error icon circle (`surface-sunken`) is subtle but visible. The title carries the meaning, so this is acceptable.
