# Update gate (iOS) — critique round 1

Context: the iOS version gate (PRD M1-UPD-2; research [ios-update.md](../../../research/ios-update.md)). Two surfaces driven by the public `appConfig/ios`: a calm, dismissible "Update available" banner docked above the tab bar on every tab when TestFlight has a newer build, and a blocking "Update required" cover when this build is below `minSupportedVersion`. Audience: the owner and invited TestFlight testers; job hunting is stressful, so the gate must stay calm and never block without a way forward. Stage: refinement (first implementation).

Captures (design mode, `-BFHRScreen today -BFHRDesign populated -BFHRUpdate available|required`): `artifacts/screens/ios/{iphone-17e,iphone-17-pro-max}/update-gate-{available,required}-{light,dark}[-ax].png` (16 captures, English).

## Design Critique: Update gate (iOS), round 1

### Overall Impression

The default-size versions do their job in two seconds: the banner says what, which version and where, with one action and a ✕, and the blocking screen has a clear title, one primary action and a quiet way to get help. The biggest problem is the largest accessibility size: the banner covers most of every tab, and the blocking screen's pinned buttons cut the explanation off mid-sentence.

### Visual Hierarchy

- **What draws the eye first**: banner — the tinted card at the bottom, then its bold title; correct for an optional notice that shouldn't compete with Today's "Next up". Blocking screen — the large title, then the teal primary button; correct.
- **Reading flow**: banner: glyph → title → sentence → action, ✕ in the corner. Blocking: glyph → title → cause + action sentence → reassurance → versions (secondary) → button → help link.
- **Emphasis**: right at default sizes. The blocking screen leaves a large empty middle on both devices; top-aligned content like the Fitbit reference keeps the text where reading starts, and the button sits where the thumb is. Acceptable.

### Consistency

| Element          | Issue                                                                                                                                                                                            | Recommendation                                   |

| Banner           | Built from the shared `InlineAlert(.info)` (glyph, title, sentence, text action, ✕), same as other notices. The info-blue title next to the teal action and ✕ is the shared component's styling. | Keep; consistent with every other `InlineAlert`. |
| Banner surface   | Opaque `Surface.elevated` under the tinted fill + `raised` elevation, so it reads over scrolled content in both themes.                                                                          | Keep.                                            |
| Blocking screen  | Tokens only: `title1` emphasized, `body`, `footnote` secondary, `bfhrPrimary` full width, `bfhrPlain`, 24 pt side margins, canvas background.                                                    | Keep.                                            |
| AX banner action | The multi-line "Open TestFlight" text action wraps with an indented first line (centered alignment inside a leading-aligned card).                                                               | Goes away with the one-line AX banner above.     |

### Accessibility

- **Color contrast** (token values from the asset catalog, light / dark): banner title `info-text` on `info-subtle` 4.64:1 / 5.27:1, sentence `fg-primary` 15.22:1 / 12.98:1, action `accent-text` 6.11:1 / 6.65:1; blocking screen on `surface-canvas`: `fg-primary` 16.26:1 / 16.39:1, versions `fg-secondary` 7.31:1 / 8.63:1, "Get help" `accent-text` 6.53:1 / 8.40:1, primary button `fg-on-accent` on `accent-solid` 6.51:1 / 4.58:1. All ≥ 4.5:1. The banner title is the tightest pair; it is semibold, and the XCUITest audit re-checks contrast on the rendered screens.
- **Touch targets**: ✕ is an `IconButton` (44 × 44); the primary is ≥ 44 pt tall; "Get help" uses `bfhrPlain` (≥ 44 pt).
- **Text readability**: default sizes fine on both devices; AX5 issues above.

### What Works Well

- Calm copy: "Update available · Version 0.2.0 is ready in TestFlight." No urgency, no exclamation marks; the blocking screen reassures that updating keeps the data.
- One way forward on the blocking screen, plus help that isn't a dead end; the installed vs required versions make support conversations easy.
- The banner is app-wide but outside each screen, so screens didn't have to change, and toasts still stack above it.

### Priority Recommendations

1. **Unpin the blocking screen's buttons at accessibility sizes** — the explanation is cut off today.
2. **Collapse the banner to one line at accessibility sizes** — it hides most of every tab.
3. **Plainer cause on the blocking screen** — "is no longer supported".

## Resolution

1. `UpdateRequiredScreen`: at accessibility text sizes the buttons follow the text inside the scroll view (no pinned bar); at default sizes they stay pinned to the bottom.
2. `UpdateBanner`: at accessibility text sizes it is one row, "Update available" as a button that opens TestFlight + ✕; the version sentence is its VoiceOver label ("Update available. Version 0.2.0 is ready in TestFlight.") with the hint "Opens TestFlight".
3. Copy: "This version of BruteForceHR is no longer supported. Install the latest version from TestFlight to continue." (TR "BruteForceHR'ın bu sürümü artık desteklenmiyor. Devam etmek için TestFlight'tan en son sürümü yükleyin.", DE "Diese Version von BruteForceHR wird nicht mehr unterstützt. Installiere die neueste Version aus TestFlight, um weiterzumachen.").
