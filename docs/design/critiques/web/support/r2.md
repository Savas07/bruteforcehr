## Design Critique: Support (`/support/`)

### Overall Impression

Ready. Answers now read correctly ("select **Advanced**, then **Go to BruteForceHR**"), the deep link opens the right question, the footer reads correctly and English no longer hyphenates. The page gives one obvious next step, a clear warning before posting publicly, and real answers to the first-run blockers.

### Visual Hierarchy

- **What draws the eye first**: "Support", then the one filled button "Open a GitHub issue". Correct.
- **Reading flow**: open answers sit directly under their question in `fg.secondary` with bold UI labels in `fg.primary`, so the steps stand out ("**More info**, then **Run anyway**").
- **Emphasis**: the rotating plus/close icon shows open state alongside the native disclosure semantics.

### Accessibility

- **Color contrast**: unchanged from r1, pass (lowest text pair: `warning.text` on `warning.subtle` 4.61:1 light).
- **Touch targets**: button, chips and question rows 44 px or taller; secondary cards fully clickable.
- **Keyboard**: Tab order skip link → logo → Support → Open a GitHub issue → Known issues → Your data and privacy → topic chips → questions; every stop shows the 2 px `line.focus` ring (secondary cards draw it on the card).

### What Works Well

- Clear expectation-setting for a one-person project without apologising.
- The privacy warning is placed before the action, in amber rather than red.
- Group titles at 1440 on the left make the 14 questions scannable at a glance.
