# iOS foundation (M0): the contract for screen work

Status: M0, 2026-10-22. How the five core iOS screens (Today, Job detail, CV editor, Tracker board, Mail review) are built, run in design mode, captured and critiqued. Design inputs: [IA.md](IA.md), [components.md](components.md), [system.md](system.md), [decisions.md](decisions.md), `research/<area>.md` and [research/states.md](research/states.md).

## Package layout

The SwiftUI layer lives in the Swift package `packages/swift/BFHRUI` (Swift tools 6.2, iOS 18, plus macOS 15 so `swift test` runs on the Mac). It depends on `BFHRCore` and `BFHRDesignTokens` only, **never on Firebase**, so screens build and test in seconds. The app target links `BFHRUI` (and `BFHRDesignTokens` for the root tint).

```

  Sources/BFHRUIFixtures/          FixtureStore: packages/fixtures/conformance/{populated,empty}.json → FixtureDocument (#if DEBUG only)
  Sources/BFHRUI/
    Foundation/                    UserData, ScreenModel/LoadPhase/ConnectionState, ToastItem, shared row data, mutations, Strings, DateText
    Components/                    shared components (catalogue below)

    Design/                        DesignScenario (launch arguments) + DesignScreenView (#if DEBUG only)
```

Concurrency: the package uses the app's model, default `MainActor` isolation with approachable concurrency (`defaultIsolation(MainActor.self)`, `NonisolatedNonsendingByDefault`, `InferIsolatedConformances`). Don't add `@MainActor`; never use `nonisolated(unsafe)`.

macOS compile rule: `BFHRUI` must also compile for macOS (that's how `swift test` runs). Use the shims in `Components/PlatformShims.swift` (`bfhrInsetGroupedList()`, `bfhrLargeTitle()`, `bfhrInlineTitle()`, `ToolbarItemPlacement.bfhrTrailing` / `.bfhrLeading` / `.bfhrBottomBar`) and put any other iOS-only API (`UIViewRepresentable`, `keyboardType`, `EditButton`, `fullScreenCover`, `UIPasteboard`) behind `#if os(iOS)`.

## Data honesty

- Design mode is **Debug-only**. `BFHRUIFixtures`, `Design/` and `apps/ios/BruteForceHR/DesignMode.swift` are wrapped in `#if DEBUG`; the build phase "Copy design fixtures (Debug only)" copies the fixture JSON into `BFHRFixtures/` of Debug app bundles only. Release builds keep the title-only shell, compile no fixture code and bundle no fixture data (verification commands below).
- Screens never import `BFHRUIFixtures`. They get a `UserData` through their model's `load(_:)`; design mode and previews fill it from fixtures, and later milestones fill it from Firestore.

## The view-model contract

Every screen model is an `@Observable final class` conforming to `ScreenModel` (`Foundation/ScreenStatus.swift`):

| Member                        | Meaning                                                                                                                                                           |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `phase: LoadPhase`            | `.loading` (cold, nothing cached → skeleton), `.failed(LoadFailure)` (nothing cached → `PaneError`), `.loaded` (cached data always wins; empty is a loaded state) |
| `connection: ConnectionState` | `.online`, `.offline(lastSyncedAt:)`, `.backOnline(syncedChanges:)` → `ConnectionBanner`, `StaleStamp`                                                            |
| `pendingSyncIDs: Set<String>` | rows changed offline → `SyncGlyph`; `recordWrite(id)` adds while offline                                                                                          |
| `load(_ data: UserData)`      | replaces the data, recomputes, sets `.loaded`                                                                                                                     |

Rules:

- Models expose typed data (dates, numbers, enums, ids), not formatted strings. Views format with `DateText` / `RelativeTimeText` and the labels in `Localization.swift`.
- Mutations are optimistic and go through `UserData+Mutations.swift` (`moveApplication`, `revertEvent`, `confirmReview`, `undoAutoChange`, `setReviewState`, `setMatchState`, `setCvArchived`), which follow BFHRCore's state machine: status moves only through `transition`, Undo only through `revert` (append-only events, D11). They return a `ToastItem`; the view calls `toastCenter.show(_:)`.
- Shared row data (`Foundation/SharedItems.swift`) keeps screens from drifting: `CompanyIdentity`, `AutoChangeItem` (`UserData.autoChanges(since:)`), `ReviewProposal` + `ReviewReason` (`reviewQueue()`), `NudgeItem` (`nudges(at:)`), `MoveTarget` (`moveTargets(for:)`), `TimelineEntry` (`timeline(for:)`).
- Each model takes `now` and `calendar` in its initializer; design mode passes the fixture's `now` (2026-10-22 07:30 UTC) so relative times are stable.

### Today — `TodayModel(now:calendar:)`

`sections: [Section]` (visible, fixed order: nextUp · toReview · followUps · deadlines · newMatches) · `nextUp: NextUp?` (interview within 48 h: company, role, title, kind, round, startsAt/endsAt, interviewer `timeZone`, meetingURL, people, prepNotes, `isJoinable` from 10 min before) · `toReview: [ReviewProposal]` + `toReviewCount` · `autoChanges: [AutoChangeItem]` (last 7 days, until acknowledged) · `followUps` / `olderFollowUps: [NudgeItem]` (≥ 14 days collapse) · `deadlines: [Deadline]` (assessment / replyBy / nextAction / jobCloses within 7 days) · `newMatches: [NewMatch]` (top 3 new, band + first reason) · `done: [DoneItem]` (until local midnight) · `isCaughtUp`, `showsConnectMailCard`, `hasMailAccount`, `accountNeedsAttention`, `profileName`.
Actions: `confirm(_:) throws -> ToastItem` · `acknowledge(_:)` · `undoAutoChange(_:) throws -> ToastItem` · `snooze(_:until:) -> ToastItem` · `notNeeded(_:) -> ToastItem` · `markDone(deadline:) -> ToastItem?` · `saveMatch(_:)` / `notForMe(_:) -> ToastItem` · `dismissConnectMailCard()`.

### Job detail — `JobDetailModel(jobId:now:calendar:)`

Missing job → `.failed(.notFound)`. `header: Header?` (title, company, locations, remoteType, remoteEligibility, employmentType, seniority, postedAt, salary + `SalaryProvenance`) · `match: MatchSummary` (`.pending` / `.noCV` / `.scored(ScoredMatch)`: score, band, basis CV, computedAt, requirement / skill / gap counts, `topReasons` (3), `topGaps` (2), full `reasons` / `gaps` / `requirements` as `Factor`, matched / unmatched skills, `rationale`) · `facts: [Fact]` (fixed order, `.notStated` values) · `description`, `hasDescription`, `isDelisted`, `originalPostingURL` · `sources: Sources` (`direct`, `boards`, `total`; per source: differing salary / title, `usedForApply`) · `applyRoute: ApplyRoute?` (`.email`, `.companySite`, `.board`, `.applied(date:applicationId:)`) · `applicationId`, `applicationStatus`, `isSaved`, `isHidden`, `hiddenReasons`, `canToggleSave`, `canHide`, `isPendingSync`.
Actions: `toggleSave() -> ToastItem?` (D02 Save: a Saved application + `created` event + match state in one batch; unsave is silent and only while the application has nothing but its `created` event) · `hide(reasons:) -> ToastItem?` · `unhide()` · `markHaveSkill(_:) -> ToastItem?` (local until the next match run) · `confirmSubmitted()` / `deferSubmitted()` / `stopApplying()` (the inline "Did you apply?" card while the job is Preparing). M4 adds `writer`, `usesSystemClock`, `writeFailures`, `applicationSummary` (the "Your application" block once applied) and `asksIfSubmitted`.
Design: populated → `job-lighthouse-senior-frontend` (rationale, a gap, 3 sources); empty → that job stripped to no description and no match. Job detail is pushed on the real Jobs stack in design mode; `-BFHRJobId <id>` opens another fixture job (e.g. `job-northstar-frontend` Preparing → prompt, `job-kumsal-frontend` Applied).

### Jobs — `JobsFeedModel(now:calendar:)`, `ApplyModel(jobId:now:)` (M4)

Source: `Sources/BFHRUI/Jobs/` and `Sources/BFHRUI/Apply/`; shared job mutations in `Foundation/UserData+Jobs.swift` (`saveJob`, `unsaveJob`, `startApplying`, `markApplied` with write-once `ApplicationPins`, `stopApplying`, `pinFiles`). Research: job-feed-search.md, apply.md, decisions.md D02 / D10 / D19 / D23 / D25.

- **Feed** (`JobsFeedScreen`): scope (`.all` / `.saved` / `.search(id)`), query (filters as you type; Return runs `jobsSearch` through `JobSearchService`), `JobFeedFilters` (the saved-search criteria applied exactly like the server's `passesSearchFilters` — `BFHRCore/SearchFilters.swift` — plus feed-only Match band and "hide unstated salary"), sort (Best match = band, then newest; Newest). Rows: save / unsave (D02), Not for me → inline "Hidden · Undo · Tell us why" row → reason sheet. "Get alerts for this search" saves the search (daily, Good+, `nextRunAt = now`) and calls `onAlertsTurnedOn` (the app asks for push permission there, D25).
- **Saved searches / Hidden jobs** (`SavedSearchesScreen`, `SavedSearchEditor`, `HiddenJobsScreen`): edit, Search now (`savedSearchRunNow`), delete with Undo; Show in feed.
- **Add a job from a link** (`JobImportReview.swift`): `JobLinkImporter` (`jobImportUrl` in the app) → review fields (low-confidence ones tagged) → `JobsFeedModel.importJob` creates the job (or updates the duplicate the server merged into), optionally Saved; the server's `jobCreatedMatch` trigger scores it. The Share Extension has its own compact sheet (`JobImport/`).
- **Apply** (`ApplySheet`): checklist (CV, cover letter: none / existing / written, route in D23 order: direct → apply email → boards; a typed recruiter address becomes the route) → company site in SFSafariViewController → "Did you apply?" → Applied with CV revision (+ PDF, cover letter) pinned, Undo; or Review email → `mailSend` from a connected sending account (10 s Undo → `mailSendCancel`) or Mail's compose sheet with the PDFs attached (`mailto:` when the device has no Mail account). PDFs are made on the device (`DeviceApplyRenderer`: cv-render + WebKit print) and stored as `renderedFiles` (`users/{uid}/rendered/{id}`).
- **Navigation**: `JobsStack` (feed root; `JobsRoute` `.job` / `.savedSearches` / `.hiddenJobs`; Apply and import sheets). Links: `bruteforcehr://jobs/{id}[/apply]`, `jobs/saved`, `jobs/searches/{id}`, `jobs/hidden`.
- **Live data**: `apps/ios/BruteForceHR/JobsTab.swift` (`JobsTabRoot`, `JobsNavigation`) and `JobsCloudServices.swift` (`CloudJobSearch`, `CloudApplyServices`, `CloudJobLinkImporter`); `FirestoreUserDataStore` also listens to `jobs`, `jobMatches`, `savedSearches`, `mailAccounts`, `renderedFiles`, and writes `jobs`, `savedSearches`, `coverLetters`, `renderedFiles`; pushed screens `attach` to it.
- **Push** (`PushNotifications.swift`): `FirebaseMessaging`, the `aps-environment` entitlement and the `remote-notification` background mode; the FCM token goes to `users/{uid}/devices/{identifierForVendor}` (runbooks/notifications.md); taps open `userInfo["link"]` through `NotificationRouter`. Works once the owner uploads the APNs key.
- **Live check**: `BFHR_DERIVED_DATA=… apps/ios/scripts/with-ios-lock.sh apps/ios/scripts/jobs-live-check.sh` seeds a throwaway user (CV + revision, 5 jobs + matches, a connected mail account when `mailSend` is deployed), runs `JobsEndToEndTests`, checks the stored documents and deletes everything.
- **Design mode**: `-BFHRScreen jobs|saved-searches|apply` (plus `job-detail`), `-BFHRApplyStep checklist|kit|prompt|email`, `-BFHRJobsSearch running|finished|failed`, `-BFHRJobsImport link|review|failed`, `-BFHRJobsPane filters|editor|hidden`; capture sub-states with `capture.sh --arg … [--tag …]`.

### CV editor — `CVEditorModel(selectedCvId:now:calendar:)` (CV Studio, M2)

List: `groups: [CVListGroup]` (base + variants, `CVVariantKind` role / language), `filter: CVListFilter`, `isEmpty` (→ Import a CV / Start from scratch), `archivedCount`. Selected CV: `document: CVDocument?` (title, language, variant info with `baseChangedSections`, template, theme, content, importedFrom, `hasLocalEdits` = this device holds a draft: failed save or conflict) · `sections: [CVSection]` (Header and Summary pinned, then `meta.sectionOrder`; `CVSectionSummary`, `items: [CVSectionItem]`, `isEmpty` → `GhostRow`) · `hiddenSections` · `revisionDays: [CVRevisionDay]` · `syncStatus: CVSyncStatus?` (`.saved(at:)`, `.saving`, `.savedOnDevice`, `.failed`) · `failedWriteIDs` · `conflict: CVConflictInfo?` · `notice: CVNotice?`.
Actions: `select(cvId:)` · item/header/summary saves · `moveSection(from:to:)` · `removeItem(sectionKind:at:) -> ToastItem?` · `archive(cvId:) -> ToastItem?` · `unarchive(cvId:)` · `rename` · `makeDefault` · `duplicate` / `newRoleVariant` / `newLanguageVariant(translate:)` (async) · `restore(revisionId:)` · `applyDesign(templateId:theme:templateName:)` · `retrySave()` · `keepThisVersion()` / `useOtherVersion()` · `createImported(…)` · `render(_:language:)`, `catalog()`, `exportFileName(format:)`, `jsonExport()`, `docxExport(paper:)`.
Services set by the app (nil in tests): `writer: CVWriter` (Firestore), `suggestionProvider` (`cvAssist`), `importer: CVImporter` (Storage + `cvImport`), `renderEngine: CVRenderEngine` (cv-render in JavaScriptCore). Design: populated → `cv-en` selected; empty → the list's empty state. `-BFHRCVPane preview|item|assist|summary|history|revision|reorder|template|export|conflict|compare|import|languageVariant` opens one pane (design importer and canned suggestions; never in Release).

#### Live data, rendering and the cv-render bundle

- `apps/ios/BruteForceHR/CVsTab.swift` puts `CVEditorScreen` on live data for the signed-in uid; `CVCloudStore.swift` (`FirestoreCVStore`: listeners on `users/{uid}`, `cvs` with metadata changes → `pendingSyncIDs`, revisions of the open CV and its base; `NWPathMonitor` → `connection`; batches; Firestore Codable mapping with `schemaVersion`) and `CVCloudServices.swift` (`CloudCVAssist`, `CloudCVImporter`). - Preview, template thumbnails, version pages and Compare show cv-render's HTML in `WKWebView` (`CVWebPage`, viewport = paper width). PDF: `CVPDFRenderer` (UIPrintPageRenderer, paper rect A4/Letter, printable rect inset by cv-render's `page.marginsMm`). DOCX: `buildCvDocxBase64` in the same bundle. JSON: the content with `meta`.

- `apps/ios/scripts/with-ios-lock.sh <command>` runs a build or UI test inside the machine-wide simulator lock (use with `BFHR_DERIVED_DATA`).
- Live check (`CVStudioEndToEndTests`, skipped without its variables): sign in a throwaway user as in "Sign-in" below (but run `testSignsInAndEditsCV` with `TEST_RUNNER_BFHR_E2E_LINK` instead of signing out), then `testImportsJSONResume` with `TEST_RUNNER_BFHR_E2E_IMPORT=<JSON Resume path on the Mac>` (Debug-only `-BFHRImportFile` skips the Files picker); verify `users/{uid}/cvs/**` through the Firestore REST API; delete the documents, `users/{uid}/cv-imports/*` and the user.

#### Live data: Today and the Tracker (M3)

- `apps/ios/BruteForceHR/TrackerTabs.swift` (`LiveUserData`, one per signed-in uid, owned by `RootView`) puts `TodayScreen`, `TrackerBoardScreen` and the Jobs tab (M4) on one `FirestoreUserDataStore` (`UserDataCloudStore.swift`): listeners on `users/{uid}`, `applications`, `applicationEvents`, `interviews`, `contacts`, `cvs`, `coverLetters`, `jobs`, `jobMatches`, `savedSearches`, `mailAccounts`, `renderedFiles` with metadata changes (pending writes → `pendingSyncIDs`; an event marks its application). `TodayModel.matchesAvailable` is on since M4; `mailAvailable` waits for M5.
- Writes: models mutate their `UserData` at once through `mutate { }`, which diffs it (`UserDataChanges`: created / updated / deleted documents, events as creates only) and hands it to the `UserDataWriter`. The store writes one batch: creates as full documents with `schemaVersion`, updates as the changed top-level fields only (so older builds never drop newer fields), deletes by id; mail messages and job matches carry only their client-writable fields. Document ids are Firestore auto ids made on the device (`UserData.makeID()`), so Undo works before the server answers. A refused batch increments `writeFailures` (toast); the listener has already restored the server's state.
- Local notifications (`ReminderNotifications.swift`): `NotificationReminderScheduler` (`UNUserNotificationCenter`, requests prefixed `bfhr.`, replaced as a whole) and `NotificationRouter` (delegate installed in `BruteForceHRApp.init`; a tap opens the reminder's link). Prep choices and "explainer shown" live in `UserDefaults` (`tracker.devicePreferences.<uid>`); sign-out removes the pending requests.
- Live check: `BFHR_DERIVED_DATA=… apps/ios/scripts/with-ios-lock.sh apps/ios/scripts/tracker-live-check.sh` creates a throwaway user (email link via the Identity Toolkit API), runs `TrackerEndToEndTests.testTrackerOnLiveData`, prints the stored documents and deletes them and the user.

Shared copy lives in `Strings` (Undo, Try again, statuses, "X · moved to Y", offline, AI disclaimer…); reuse it instead of re-adding a string.

Strings that interpolate user data (email addresses, domains, company names) render with `Text(bfhrPlain: resource)`: plain `Text(resource)` turns an address into an accent-colored `mailto:` link inside the sentence. The shared components already do this.

Accessibility audits (`performAccessibilityAudit` in each screen's UI tests): avoid `.accessibilityElement(children: .combine)` around views that contain buttons, and `ViewThatFits` around text (the audit reports both as unsupported Dynamic Type). Issues the audit reports without an element are nodes XCUITest can't resolve (rows cut by the viewport, cells the list keeps off screen); every screen's audit logs them for review instead of failing, so a screen-specific rule isn't needed.

Navigation between tabs: open `bruteforcehr://…` links with `@Environment(\.openURL)` (IA.md "Deep links"). `RootView` handles them in-app (no round trip through the system) by selecting the link's tab; other schemes go to the system. Links only switch tabs in M0; pushing the linked item and the `settings` host (Settings sheet) land with those screens.

## Sign-in

Email-link sign-in (ADR 0003, M1). Signed out, `RootView` shows `SignInScreen` instead of the tabs (Release, and Debug without design arguments); design mode skips it. `SignInModel` (BFHRUI, tested with a fake service in `SignInTests`) owns the steps (`enterEmail` → `checkEmail` → `finishing` → signed in, plus `confirmEmail` for a link from another device and `linkFailed(expired / unusable / accountDisabled / retryable)`), the remembered address (`SignInStore`: pending email for the link, send time for the 60 s resend cooldown, last address to pre-fill after sign-out) and URL handling. `SignInLink` turns every URL shape the link arrives in (`/__/auth/links?link=…` on `bruteforcehr.firebaseapp.com`, the action URL, `bruteforcehr.web.app/auth/finish?…`, `bruteforcehr://auth/finish?link=…`) into Firebase's action URL: FirebaseAuth 13 doesn't unwrap `link=` itself. `RootView` routes `onOpenURL` and `onContinueUserActivity(NSUserActivityTypeBrowsingWeb)` through `SignInModel.handles(_:)` before the tab links. While signed in, `\.bfhrAccount` turns `AvatarButton` (and the shell's avatar) into `AccountMenu` (Signed in as …, Sign out).

Associated Domains (`apps/ios/BruteForceHR.entitlements`) cover both Hosting hosts; the AASA on the Hosting site lists `/__/auth/links*`, `/__/auth/action*` and `/auth/finish*` for `67NPXV7CSZ.com.savas07.bruteforcehr`. Automatic signing provisions the capability (the team profile `iOS Team Provisioning Profile: com.savas07.bruteforcehr` carries `associated-domains`).

Live check against project `bruteforcehr` (`SignInEndToEndTests`, skipped without its variables): run `testSendsLink` with `TEST_RUNNER_BFHR_E2E_EMAIL=<test address>`; create a link for the same address with `POST https://identitytoolkit.googleapis.com/v1/projects/bruteforcehr/accounts:sendOobCode` (`requestType: EMAIL_SIGNIN`, `continueUrl: https://bruteforcehr.web.app/auth/finish`, `canHandleCodeInApp: true`, `iOSBundleId`, `returnOobLink: true`; `gcloud auth print-access-token` + `x-goog-user-project: bruteforcehr`); run `testOpensLinkThenSignsOut` with `TEST_RUNNER_BFHR_E2E_LINK=<oobLink>` too; then delete the test user (`accounts:delete`).

## Strings

- `LocalizedStringResource.bfhr("<screen>.<key>", default: "English", table: "<Screen>", comment: "…")`; `Text(resource)` renders it. Keys are semantic; the English default sits in code and in the catalog's `en` value.
- Add every key to `<Screen>/<Screen>.xcstrings` with `en`, `tr` (formal **siz**) and `de` (informal **du**), `"extractionState" : "manual"`. ## Adding a screen (screen agents)

You own `packages/swift/BFHRUI/Sources/BFHRUI/<Screen>/**`, `Tests/BFHRUITests/<Screen>ModelTests.swift` and `docs/design/critiques/ios/<screen>/**`. Nothing else.

1. Replace `<Screen>Screen.swift` (the M0 data rendering) with the real design. Keep the public initializer `<Screen>Screen(model:)`; design mode, previews and the capture harness call it.
2. Wrap the content in `PhaseContainer(model.phase) { … } skeleton: { … } failure: { … }`, put `ConnectionBannerSection(model.connection)` first in the list and apply `.bfhrToastHost()`; read `ToastCenter` with `@Environment(ToastCenter.self) private var toasts: ToastCenter?`.
3. Extend the model in your folder when the design needs more data (with tests). Use the shared builders and mutations; don't duplicate them.
4. Render all five states: `populated`, `empty` (states.md's Empty column for your screen; adjust `<Screen>Design.swift` if the empty fixture needs a variant), `loading`, `error`, `offline`, in light and dark, at the default and the largest accessibility text size.
5. Run the package tests, build the app, capture, critique (below), iterate.

**Not yours** (ask the foundation owner or Main): `Package.swift`, `Foundation/`, `Components/`, `Design/`, `Resources/`, other screens' folders, `apps/ios/**`. ## Build, test, capture

```sh
# View-model + catalog tests (macOS, seconds)
cd packages/swift/BFHRUI && swift test

# App (Debug, simulator) into this worktree's DerivedData
cd apps/ios && xcodebuild build -project BruteForceHR.xcodeproj -scheme BruteForceHR \
  -derivedDataPath build/DerivedData -destination 'platform=iOS Simulator,name=iPhone 17e' -quiet

# Captures: one screen × all five states × light/dark × both devices × default and AX sizes
apps/ios/scripts/capture.sh --screen today --size default --size ax
#   → artifacts/screens/ios/<device>/<screen>-<state>-<theme>[-ax].png
#   options: --state NAME (repeatable), --theme light|dark, --device NAME, --skip-build, --screen all
# Update gate over Today: --screen update-gate (states available, required) → update-gate-<state>-<theme>[-ax].png
# Sign-in: --screen sign-in (states email, invalid, offline, check, resent, finishing, confirm, expired, unusable, retry)
#   → sign-in-<state>-<theme>[-ax].png. The title-only tab shell (no --screen) needs a session on the simulator.
```

- DerivedData is per worktree (`apps/ios/build/DerivedData`, gitignored), so worktrees build in parallel. The simulators are shared: the capture step takes a machine-wide lock (`/tmp/bfhr-ios-capture.lock`) and waits for another worktree's capture to finish.
- Measured on this machine (M0, Xcode 26.6): the first app build in a fresh worktree compiles the Firebase SDK, about 1.5 min and 2.5 GB of DerivedData. After a one-line view change in `BFHRUI`: `xcodebuild build` 16.5 s, `build-for-testing` (what `capture.sh` runs) 25 s, `swift build` of the package 6 s. A capture of one screen × 5 states × 2 themes × 2 sizes × 2 devices takes about 8.5 min.
- A design capture waits until the screen's tab is selected and then for either the design root (`design.<screen>`, set by `DesignScreenView`) or the back button of a view the screen pushed over it, so screens that open a detail at launch (CV editor) capture without failing the run.
- Delete `apps/ios/build/` when your screen is done (disk is tight).

## Share Extension (M4)

`BruteForceHRShare` (`apps/ios/BruteForceHRShare/`, bundle `com.savas07.bruteforcehr.share`, embedded in the app) adds "BruteForceHR" to the system share sheet for one web URL or text. `ShareViewController` reads the shared URL (or the text; the server finds the first link) and hosts `JobImportShareSheet` (BFHRUI `JobImport/`, model `JobImportShareModel`, table `JobImport`). `FirebaseShareService` calls `jobImportUrl` and writes, in one batch, the job (create, or update of the existing duplicate) plus an application in Saved or Applied and its `created` event (decisions.md D02); the `jobCreatedMatch` trigger adds the match.

- **Shared session**: both targets compile `apps/ios/Shared/SharedSession.swift`. `useSharedKeychain()` moves the Firebase Auth session into the keychain access group `$(AppIdentifierPrefix)com.savas07.bruteforcehr.shared` (Info.plist `BFHRKeychainAccessGroup`; a session from an older build is carried over). The App Group `group.com.savas07.bruteforcehr` holds a link shared while signed out (`pendingSharedJobURL`). Automatic signing registers the extension id, the group and the keychain group for team 67NPXV7CSZ. Unsigned builds (CI archive) have no entitlements and keep the default keychain.
- **Design mode**: `-BFHRShareSheet <reading|ready|ai|existing|saved|logged|blocked|offline|signed-out|manual>` shows the sheet in the app (the extension can't take arguments). `capture.sh --screen share-sheet` captures it, and `ShareSheetAccessibilityAuditTests` audits every state at the default and AX5 sizes, plus TR and DE.
- **Live check**: `BFHR_DERIVED_DATA=… apps/ios/scripts/with-ios-lock.sh apps/ios/scripts/share-live-check.sh` signs a throwaway user in, opens a posting in Safari, then runs Share → BruteForceHR → Save and log as applied. It reads the documents back and deletes everything (`ShareExtensionEndToEndTests`).
