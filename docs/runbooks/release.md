The pipeline itself is specified in [ADR 0004](../adr/0004-release-updates-signing.md). The client stack is in [ADR 0007](../adr/0007-native-ios-tauri-desktop.md). This runbook covers the **secrets inventory** (BRIEF §7.5), the one-time setup, releasing, dry runs and rollback.

If Actions is ever unavailable, a release can be built and signed on the owner's Mac, because the updater key is local (["Updater key offline backup"](#updater-key-offline-backup)).

The source repo `Savas07/bruteforcehr` is **public, view only** under the proprietary [`LICENSE`](../../LICENSE): private on 2026-10-25 for a few hours, then public again by the owner's choice. Releases (installers, `latest.json`, `SHA256SUMS.txt`), the `updater-beta` manifest and public support issues live in the **public** repo **`Savas07/bruteforcehr-releases`** ([ADR 0004 addendum 2026-10-24](../adr/0004-release-updates-signing.md#addendum--2026-10-24-private-source-public-releases-repo)). Version tags stay in the source repo; the releases repo gets the same tag on its default branch when a release is published.

**Every secret below is CI-only.** They are GitHub Actions secrets on `Savas07/bruteforcehr` (Settings → Secrets and variables → Actions), read only by `release.yml` jobs. None of them goes into a client bundle, Firestore, chat or a commit. How to create each Apple value: [accounts.md](accounts.md) §6. Runtime secrets of the functions (Anthropic, OAuth, job APIs) are in Secret Manager, not here ([accounts.md](accounts.md) §2–5).

`RELEASES_REPO_TOKEN` is the only GitHub token secret. Everything in the source repo uses the workflow's `GITHUB_TOKEN` with per-job permissions (`contents: write` only in `publish`, for the v0.3.0 bridge; remove it with the bridge).

Not secrets and committed: the updater **public** key (`tauri.conf.json`), `GoogleService-Info.plist` and the Firebase web config (client config). `ExportOptions.plist` is generated by the `ios` job.

Rules for the workflow:

- Secrets are exposed only as `env` on the step that needs them. Files written from secrets (`.p8`) live in `$RUNNER_TEMP` and are deleted in an `if: always()` step.
- Real releases run only on `v*` tags (pushed by `version.yml` or the owner). `pull_request` workflows never get these secrets, and pull requests from forks get neither secrets nor an OIDC token for Workload Identity Federation.

### Releases repo token

`release.yml` writes to `Savas07/bruteforcehr-releases` with a fine-grained personal access token (the workflow's `GITHUB_TOKEN` can't write to another repo). Create it as `Savas07`:

1. Open **https://github.com/settings/personal-access-tokens/new**.
2. **Token name** `bruteforcehr release publishing`; **Expiration** custom, **1 year** from today; **Resource owner** `Savas07`.
3. **Repository access:** **Only select repositories** → `Savas07/bruteforcehr-releases` (nothing else).
4. **Permissions → Repository permissions → Contents: Read and write.** Metadata: Read-only is added automatically. No other permission.
5. **Generate token**, copy it once, and store it straight into the source repo's secrets (it never goes into chat, a file or a commit):

   ```sh
   gh secret set RELEASES_REPO_TOKEN --repo Savas07/bruteforcehr   # paste at the prompt, Enter
   gh secret list --repo Savas07/bruteforcehr                       # shows RELEASES_REPO_TOKEN and its date
   ```

**Rotation:** GitHub emails before the token expires. Create a new token the same way, run the `gh secret set` again, then delete the old token at github.com/settings/personal-access-tokens. Do the same at once if the token may have leaked. A leaked token can change releases in `bruteforcehr-releases` but can't ship an update: clients only install bundles signed with the updater key (ADR 0004 §3); after a leak, check the releases' `latest.json` against `SHA256SUMS.txt` from the run summary.

### Updater key offline backup

`~/.bruteforcehr/updater/` on the owner's Mac (directory `700`, files `600`):

- `bruteforcehr-updater.key` — the private key (minisign, encrypted with the password)

## Releasing

1. Add a changeset to every user-facing PR: `pnpm changeset` (any `@bfhr/*` package; one fixed group, so the whole app moves together).
2. On merge to `main`, `version.yml` opens or updates the **"chore: version packages"** PR (versions + CHANGELOG.md files). A PR opened with `GITHUB_TOKEN` doesn't start `ci.yml`; close and reopen it if you want CI on it.
3. Merge that PR. `version.yml` then tags `vX.Y.Z` (source repo) and starts `release.yml` on the tag; its `prepare` job creates the **draft** release with the notes in `Savas07/bruteforcehr-releases`.
4. `release.yml` runs `prepare` → `verify` (full CI) + `verify-desktop` (`desktop.yml` E2E on macOS + Windows) + `desktop-mac` + `desktop-win` + `ios` → `backend` → `publish` → `website`. It is green only when every job passed. A failed job leaves the draft unpublished; fix forward with a new patch version.
5. **Beta:** `pnpm changeset pre enter beta`, merge the version PR, then push the tag yourself: `git tag v0.2.0-beta.0 && git push origin v0.2.0-beta.0` (the tag must equal `apps/desktop/package.json`'s version). The release is published as a pre-release and only `updater-beta` gets its manifest. `pnpm changeset pre exit` returns to stable versions.
6. Check:
   - The release page (https://github.com/Savas07/bruteforcehr-releases/releases) lists `BruteForceHR_X.Y.Z_universal.dmg`, `…_universal.app.tar.gz` + `.sig`, `…_x64-setup.exe` + `.sig`, `latest.json` and `SHA256SUMS.txt`.
   - `curl -sL https://github.com/Savas07/bruteforcehr-releases/releases/latest/download/latest.json` shows `X.Y.Z` (stable); `https://github.com/Savas07/bruteforcehr-releases/releases/download/updater-beta/latest.json` shows the newest stable or beta.
   - `appConfig/macos` and `appConfig/windows` show `latestVersion: X.Y.Z` (and `appConfig/ios` once TestFlight uploads run).
   - TestFlight shows build `X.Y.Z (<run number>)` (once the Apple secrets exist).
   - `https://bruteforcehr.web.app/download` shows `X.Y.Z`.
7. M1 acceptance (BRIEF §7): install `v0.1.0` on clean macOS and Windows, publish `v0.1.1`, confirm both update with only "Restart", TestFlight gets `0.1.1`, and the website shows `0.1.1`. Repeatable on hosted runners: `gh workflow run update-acceptance.yml -f from=X.Y.Z -f target=X.Y.Z+1`. Results: [M1 acceptance](#m1-acceptance).

**Raising `minSupportedVersion`:** edit `scripts/release/min-supported-versions.json` in the PR that needs it (never above the version being released; `publish` refuses that). It takes effect with that release's `appConfig` write.

On each clean runner it:

1. checks that the stable `latest.json` says `0.1.1`, downloads the v0.1.0 installer from the release and checks it against `SHA256SUMS.txt`;
2. installs like a user: macOS mounts the DMG and copies `BruteForceHR.app` to `/Applications` (`CFBundleShortVersionString` 0.1.0); Windows runs the NSIS installer per-user with `/S` (uninstall entry `DisplayVersion` 0.1.0, `bruteforcehr.exe` ProductVersion 0.1.0);
3. launches the installed app; its own background check reads the real manifest, verifies the signature and downloads 0.1.1 (`update check: 0.1.1 downloaded, installs at quit` on stderr);
4. quits the app the way a user does, and the app installs the update on its normal exit path (`installing update 0.1.1 at quit`): macOS sends the Quit Apple Event (`NSRunningApplication.terminate()`, the same event as ⌘Q / app menu Quit / Dock Quit); Windows sends `WM_CLOSE` to the main window (the title bar's close button / Alt+F4), and the app starts the downloaded installer in passive mode and exits 0;
5. asserts the installed version: macOS `CFBundleShortVersionString` **0.1.1** and `codesign --verify --deep --strict` passes; Windows `DisplayVersion` **0.1.1** and `bruteforcehr.exe` ProductVersion / FileVersion **0.1.1**;
6. relaunches: the app reports `update check: up to date`.

Quit-then-relaunch is the "restart" of BRIEF §7: the in-app **Restart to update** button runs the same `Update::install` and then relaunches (`updater::restart_to_update`); the run drives quit because it needs no UI automation. The first run, [39898073734](https://github.com/Savas07/bruteforcehr/actions/runs/39898073734), passed on macOS and showed that Windows ends a step's processes when the step ends (the app was gone before the quit step), so the Windows launch, download and quit now share one step.

What it doesn't prove, and what's pending:

- **Developer ID signing + notarization** (Apple secrets pending): the macOS app is ad-hoc signed. `gh release download` sets no quarantine flag, so the runner doesn't show Gatekeeper's first-open block; a user who downloads the DMG with a browser has to choose **Open Anyway** once. The updater's own swap of the bundle doesn't involve Gatekeeper.
- **Windows Authenticode** (no certificate, ADR 0004): SmartScreen may warn on the first install; updates are verified by the Tauri updater signature.
- **TestFlight 0.1.1**: the `ios` job built an unsigned archive and uploaded nothing (`APPLE_API_KEY_*` / `APPLE_TEAM_ID` pending), so `appConfig/ios` wasn't written.

## App icon in CI builds

The macOS icon is the Icon Composer file `apps/desktop/src-tauri/icons/AppIcon.icon` (listed in `bundle.icon`); Tauri compiles it with `actool` into `Contents/Resources/Assets.car` and sets `CFBundleIconName`. On GitHub's macos-26 runners (Xcode 26.6) the `actool` that `tauri build` / `tauri bundle` starts throws `-[__NSPlaceholderArray initWithObjects:count:]: attempt to insert nil object` on it in every run (release run [39890227250](https://github.com/Savas07/bruteforcehr/actions/runs/39890227250), every macOS Desktop run since `fd50794`, debug runs [39892026876](https://github.com/Savas07/bruteforcehr/actions/runs/39892026876), [39892408284](https://github.com/Savas07/bruteforcehr/actions/runs/39892408284) with a fresh `ibtoold`, and [39892805795](https://github.com/Savas07/bruteforcehr/actions/runs/39892805795), which logs the environment and arguments Tauri gives `actool`), and the `ibtoold` server it leaves behind then fails later calls from a shell too (39892026876). The same `actool` arguments from a shell compile it on the same runners with every installed Xcode 26.x, warm or cold, from any directory, with Tauri's environment variables, with stdin closed and from a non-shell parent (debug runs [39891582181](https://github.com/Savas07/bruteforcehr/actions/runs/39891582181), [39891883545](https://github.com/Savas07/bruteforcehr/actions/runs/39891883545), [39893243885](https://github.com/Savas07/bruteforcehr/actions/runs/39893243885), [39893363214](https://github.com/Savas07/bruteforcehr/actions/runs/39893363214)). No other build runs concurrently in those jobs, and Tauri starts `actool` once per bundle (`--version`, then the compile).

So CI precompiles it: `apps/desktop/scripts/compile-app-icon.sh <dir>` runs `actool` on the `.icon`, then prints a config overlay whose `bundle.icon` lists that `Assets.car` instead of the `.icon`. Tauri copies a listed `.car` into the app as is and reads `CFBundleIconName` from it, so the shipped icon is the same. `release.yml` (`desktop-mac`, which also checks `Assets.car` and prints `CFBundleIconName`) and `desktop.yml` (macOS bundle) pass the overlay with `--config`. Local builds (`pnpm bundle`) use the `.icon` directly. When a Tauri or Xcode update makes `tauri build` compile the `.icon` on the runner again, drop the script and the two `--config` flags.

## Dry run

Builds and signs everything, verifies the updater signatures, assembles `latest.json` + `SHA256SUMS.txt` (artifact `release-assets-dry-run`, kept 14 days), checks the deploy identity (`firebase projects:list`, `firebase deploy --dry-run`, a read of `appConfig`) — and publishes, tags, uploads and deploys nothing.

```sh
# The `release` environment only admits `v*` tags and `release-dry-run/**` branches, so a dry run
# (`gh workflow run release.yml --ref main …` is rejected) is a push of the commit to test:
git push origin HEAD:refs/heads/release-dry-run/0.1.0
gh run download <run-id> -n release-assets-dry-run
```

Delete the `release-dry-run/*` branch afterwards. First green dry run of the whole pipeline (v0.1.0, without Apple secrets): run [39878542834](https://github.com/Savas07/bruteforcehr/actions/runs/39878542834).

## Halting and rolling back

See [ADR 0004](../adr/0004-release-updates-signing.md) §5. To stop desktop clients picking up a bad `vX.Y.Z`, replace its `latest.json` (and the one on `updater-beta`) with the previous release's:

```sh
gh release download vX.Y.(Z-1) --repo Savas07/bruteforcehr-releases --pattern latest.json --dir /tmp/prev
gh release upload vX.Y.Z --repo Savas07/bruteforcehr-releases /tmp/prev/latest.json --clobber
gh release upload updater-beta --repo Savas07/bruteforcehr-releases /tmp/prev/latest.json --clobber
```

Then ship `X.Y.Z+1`. Never delete a published release.

## Moving releases to bruteforcehr-releases

Installed apps up to **0.2.2** read their manifests from the source repo (`Savas07/bruteforcehr/releases/…/latest.json`); 0.3.0 and later read `Savas07/bruteforcehr-releases`. Order, once:

1. **Done 2026-10-24:** `bruteforcehr-releases` bootstrapped; v0.2.2 mirrored there (installers, updater bundles + `.sig`, `SHA256SUMS.txt` without its `latest.json` line, same notes), so the website keeps a download when it builds from the new repo. No `latest.json` was mirrored: its URLs pointed at the source repo.
2. **Done 2026-10-24:** owner created `RELEASES_REPO_TOKEN` ([Releases repo token](#releases-repo-token)); due for rotation by 2027-10-24.
3. Merge this change, then the **v0.3.0** version PR (#17). `release.yml` publishes v0.3.0 in `bruteforcehr-releases` and, in the step marked **`BRIDGE v0.3.0`**, also publishes release `v0.3.0` in the source repo with only its `latest.json` (marked latest) and uploads it to the source repo's `updater-beta`. Those manifests point at the new repo's assets, so 0.1.x/0.2.x installs update to 0.3.0 and from then on poll the new repo.
4. Check before going private: `curl -sL https://github.com/Savas07/bruteforcehr/releases/latest/download/latest.json | jq .version` and the same for `bruteforcehr-releases` both print `0.3.0`, and the URLs in it start with `https://github.com/Savas07/bruteforcehr-releases/`. Optionally `gh workflow run update-acceptance.yml -f from=0.2.2 -f target=0.3.0` (macOS + Windows minutes).
5. Leave the source repo public for a few days so running installs pick up 0.3.0 (they check at launch and every 6 h).
6. **Done 2026-10-25:** `Savas07/bruteforcehr` went private (owner's call). At the switch, both repos' `latest.json` served 0.4.0. Later that day the owner made it public again with a proprietary `LICENSE`; installs keep updating from `bruteforcehr-releases` either way.
7. **Done 2026-10-25:** the `BRIDGE v0.3.0` step is deleted and `publish` has `contents: read` (checkout only). Installs still on ≤ 0.2.2 need a one-time download from https://bruteforcehr.web.app/download.

**Typical month within 2,000:** 2 releases (~940) + 3 desktop runs (~720) + ~50 CI/version runs (~300) ≈ 1,960. Beyond that: batch desktop changes into fewer PRs, prefer one dry run per pipeline change, run design captures only for final critique rounds, or set a small spending limit in Settings → Billing. If minutes get tight, `verify-desktop` is the first thing to drop from releases (`desktop-mac`/`desktop-win` still build, lint and unit-test the app). Check usage at github.com/settings/billing/usage. Artifact storage on Free private repos is 500 MB; desktop artifacts expire after 14 days.

## Functions: memory and cost of `cvRenderPdf`

`cvRenderPdf` (server PDF render, [ADR 0009](../adr/0009-cv-rendering.md)) runs headless Chromium from `@sparticuz/chromium` 153.0.0 (Chromium 153.0.8010.36) driven by `puppeteer-core` 25.11.0, the pair pptr.dev/chromium-support lists for that build. Bump the two together and `SERVER_CHROMIUM_VERSION` in `apps/functions/src/render/print.ts`; the functions test checks the version.

- **Settings:** 2 GiB, 1 vCPU, concurrency 4 (one shared browser per instance, one page per request), timeout 120 s, `maxInstances` 10 (global). 2 GiB because Chromium unpacks (~180 MB) into `/tmp`, which is memory on Cloud Run, and needs a few hundred MB per page on top.
- **Cold start:** unpacking Chromium and launching the browser adds a few seconds to the first request of an instance; warm requests take about a second per CV.
- **Cost (Cloud Run functions, tier-1 region, list price):** about $0.000024 per vCPU-s plus $0.0000025 per GiB-s, i.e. ~$0.00003 per second of this function; a warm render of ~1–2 s costs well under $0.0001, a cold one under $0.0005. The monthly free tier (180,000 vCPU-s, 360,000 GiB-s, 2 M requests) covers a personal account entirely, far below the ₺250 budget alert.
- **Check after a deploy:** `pnpm --filter @bfhr/functions smoke:render` (creates a throwaway user, renders a CV, verifies the stored bytes against `sha256`, deletes everything).
